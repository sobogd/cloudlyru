# CloudlyRu

Личное self-hosted облако: сервер на VPS и приложения (Flutter) на Android, macOS, iPad и
iPhone. Прод — <https://files.iq-factura.com>, репозиторий — `sobogd/cloudlyru`.

Принцип хранения: файлы лежат объектами в S3 (Hetzner Object Storage) с адресацией по
SHA-256 (одинаковое содержимое не дублируется), дерево папок, метаданные, доступы и
корзина — в Postgres на том же VPS.

## Что внутри

| Каталог | Что это |
|---|---|
| `src/` | API (NestJS + Prisma): авторизация, файлы и папки, загрузки (в том числе частями прямо в S3), превью и конвертация медиа, корзина, WebDAV, журнал изменений для клиентов |
| `flutter/` | Мобильное приложение (Flutter, Android): файлы, почта, медиа, карта, корзина, настройки и синхронизация папок телефона |
| `deploy/` | nginx-конфиг, pm2-процесс, серверные скрипты (бэкап БД, уборка сирот в бакете) |
| `scripts/` | Утилиты: публикация APK, локальные проверки контрактов и медиа-метаданных, backfill'ы метаданных, выгрузка Google Takeout |
| `prisma/` | Схема БД и миграции |

Веб-клиента и нативного Android-клиента в проекте больше нет: браузерных страниц сервер не
отдаёт вовсе, единственный клиент — приложение из `flutter/`.

Раздел «Медиа» — не вся зона «Фото», а ровно то, у чего есть строка `MediaMeta` (её заводит
разбор метаданных для любого `image/*` и `video/*`). PDF, архивы и прочее в ленту не попадают
вовсе, BMP/JXL попадают без превью (`previewState = 'impossible'`); всё это видно в «Файлах».

Документация: [`DEPLOY.md`](DEPLOY.md) — деплой и эксплуатация, [`FLUTTER.md`](FLUTTER.md) —
как устроено и почему так сделано мобильное приложение, [`PLAN.md`](PLAN.md) — план развития
и принятые решения.

## Локальный запуск

```bash
pnpm install
cp .env.example .env          # DATABASE_URL, ADMIN_LOGIN/ADMIN_PASSWORD; ключи S3 — по желанию
pnpm exec prisma migrate deploy
pnpm build && pnpm start      # http://127.0.0.1:8305
```

Без ключей S3 поднимается только API: файловые операции требуют объектного хранилища.

## Прод

Автодеплой: push в `main` по путям `src/**`, `prisma/**`, `package.json`,
`pnpm-lock.yaml`, `.env.example` → GitHub Actions (`.github/workflows/deploy.yml`) собирает
сервер, кладёт бандл на VPS и перезапускает pm2 `cloudlyru` (:8305, только локально)
за nginx `files.iq-factura.com`. Ручной запуск — `gh workflow run deploy.yml`.

Сборки приложений — тоже в GitHub Actions: push по путям `flutter/**` поднимает
`.github/workflows/android.yml`, `macos.yml` и `ios.yml` (подробности — «Как выпустить новую
сборку»). Пути разделены намеренно: менялся сервер — идёт только деплой, менялся клиент —
только сборки приложений; если в одном коммите и то и другое, запускаются все четыре workflow.

Проверка: `curl -s https://files.iq-factura.com/api/v1/healthz` → `{"ok":true,…}`.

## Мобильное приложение: одна ссылка и обновление по кнопке

**Скачать приложение: <https://files.iq-factura.com/apk>** — ссылка постоянная и всегда
отдаёт последнюю опубликованную сборку. Версию, размер и sha256 этой сборки отдаёт
`GET /api/v1/app/android`; если сборки ещё нет (или рядом с APK нет описания `latest.json`),
ручка отвечает 404 с кодом `no_release`. Состояние публикации видно и без авторизации:
`GET /apk/version` → `{published: true, …}` либо `{published: false[, fileAvailable: true]}`.

В приложении есть «Проверить обновление» (проверяется и само при старте): если на сервере
лежит сборка с большим `versionCode`, появляется карточка с кнопкой **«Обновить»** — она
скачивает APK, проверяет его по размеру и sha256 и открывает системный установщик.
Полностью молча обновиться APK-приложение не может: Android в любом случае показывает
диалог установки, и подтвердить его нужно один раз. Браузер, поиск файла в «Загрузках»
и ручной выбор APK при этом не нужны.

### Как выпустить новую сборку

Релизы собирает GitHub Actions: push в `main` по путям `flutter/**` поднимает три workflow —
`.github/workflows/android.yml`, `macos.yml`, `ios.yml` (`deploy.yml` в это же время деплоит
сервер, если менялся `src/**`). Номер версии поднимает человек: по нему телефон и понимает,
что вышло обновление.

1. Поднять `versionCode` (и `versionName`) в `flutter/pubspec.yaml` (`version: 1.0.0+45`).
2. Push в `main`.
3. Actions собирает **три** платформы на этот номер и публикует их: APK — в `/apk`,
   `Cloudly.app` — в `/macos`, `.ipa` — в `/ios` (установка по воздуху — `/ios/install`).
   Номер общий для платформ, поэтому все три уходят одним заходом: опубликоваться позже
   с тем же номером платформа уже не сможет.
4. За ходом следить не нужно: результат появляется сам, а работу приложения проверяет владелец.
   Ручной перезапуск — `gh workflow run android.yml` (или `macos.yml`, `ios.yml`), а
   `-f force=true` пересобирает тот же номер для проверки на устройстве.

Если номер не поднят, workflow падает с понятным сообщением: сборка с тем же номером не
появится в приложении как обновление, а тихо подменять файл по ссылке — значит оставить
телефон на старой версии.

Локальная сборка осталась запасным путём: `./scripts/build-release.sh all` быстрее холодного
раннера (инкремент) и умеет `--force`. Публикуют оба пути одними и теми же скриптами
`scripts/publish-*.mjs`.

Вручную (например, чтобы опубликовать уже собранный APK):

```bash
node --env-file=$HOME/work/.env scripts/publish-apk.mjs \
  flutter/build/app/outputs/apk/release/app-release.apk          # + --dry-run, чтобы только посмотреть
```

Сборка на маке:

```bash
cd flutter
flutter build apk --release
```

Релиз подписывается ключом из `flutter/android/keystore.properties` (в git не попадает).
Ставится APK поверх только той же подписью: ключ терять нельзя, иначе обновление потребует
удаления приложения.

```bash
pnpm build                                    # сервер компилируется
cd flutter && flutter analyze                 # статический анализ клиента

# контрактные проверки на локальной БД (не на проде), нужен собранный dist:
DATABASE_URL=postgresql://user@127.0.0.1:5432/cloudly_dev node scripts/m3-sync-check.mjs
DATABASE_URL=postgresql://user@127.0.0.1:5432/cloudly_dev node scripts/media-meta-check.mjs
```
