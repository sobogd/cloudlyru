# CloudlyRu Android — клиент телефона

Статус: **сделано и работает на телефоне**. Дополняет `PLAN.md` (§16, этап M3).
Инструкция по установке и сборке — `android/README.md`.

## Итоговая модель (согласовано)

Приложение делает четыре вещи и намеренно не делает ничего больше:

1. **Автозагрузка выбранных папок** телефона в облако. Односторонняя: только телефон → облако.
2. **Файловый браузер облака** средствами Android — провайдер документов, виден в системных
   «Файлах», в выборе файлов и в диалогах сохранения. Плюс «сохранить в облако» из других
   приложений и открытие файла из облака.
3. **«Поделиться»** в облако: приложение в системном списке, папка получателя выбирается в нём же.
4. **«Освободить место»** — вручную и только по нажатию: убрать с телефона то, что уже
   подтверждено в облаке.

Чего не делаем принципиально:

- приложение **не удаляет** файлы с телефона само и **не удаляет/не перезаписывает** файлы
  в облаке по своей инициативе (единственные удаления — по нажатию пользователя: «освободить
  место» на телефоне и «удалить» в файловом браузере, а второе уходит в корзину сервера);
- изменений в вебе телефон не боится: удалили файл в облаке — на телефоне он остаётся;
- удалили файл на телефоне — копия в облаке остаётся (архивная семантика, не зеркало);
- **никакого скачивания облака на телефон** нет; файл попадает на телефон, только когда его
  открывают из файлового браузера (и ложится в кэш приложения).

## Решения (зафиксировано)

- **Только Android, только APK, sideload.** В Google Play не идём: нужен
  `MANAGE_EXTERNAL_STORAGE` («Доступ ко всем файлам»), без него не видно корня `Download/` и
  произвольных папок. SAF для задач синхронизации не используем: нужны обычные пути, быстрый скан
  и `setLastModified`.
- **Зона — следствие целевой папки:** «Фото» (сервер делает превью и показывает в таймлайне,
  файлы ложатся плоско) или «Файлы» (как есть, со структурой подпапок).
- **Идентичность файла — `sha256`.** `mtime` — только дешёвый предфильтр, не истина.
- **Дедуп до передачи байтов:** спрашиваем сервер, что из содержимого у него уже есть; если есть —
  запись создаётся без загрузки.
- **Чужое имя не перезаписываем и файлы на телефоне не трогаем.** Если в целевой папке имя занято
  другим содержимым, суффикс `IMG_0001 (2).jpg` получает только запись в облаке — локальный файл
  остаётся как был (приложение не переименовывает и не переносит файлы пользователя).
- **Переименование на телефоне — это `move`,** а не «удали + залей»: id записи сохраняется,
  в облаке не появляется дубль, второе устройство видит перемещение.
- **Журнал изменений (`/sync/changes`) клиент не использует.** Он остаётся серверным механизмом для
  веба и на случай возврата двусторонней синхронизации; односторонней загрузке он не нужен.
- **Никакого автоудаления.** `keepDays`, «вытеснение», тройные состояния
  (`синхронизирован/вытеснен/не выгружен`), «держать офлайн» и недельная сверка — **сняты**
  вместе с двусторонней моделью. Кэш приложения (`путь → размер, mtime, sha`) остаётся: без него
  библиотека хэшировалась бы целиком на каждом проходе.

## Как устроен клиент

```
android/app/src/main/java/ru/cloudly/sync/
  App.kt            зависимости, каналы уведомлений, периодика WorkManager
  data/Db.kt        SQLite: задачи (jobs), кэш выгруженного (cache), очередь (ops), kv
  data/Prefs.kt     адрес и device-токен (EncryptedSharedPreferences, откат с предупреждением)
  net/Api.kt        REST: have, ensure-path, children (с пагинацией), uploads, previews, файлы
  net/Dto.kt        разбор ответов сервера
  sync/Hasher.kt    SHA-256, обход папки (Scanner), определение mime
  sync/Decisions.kt чистые правила: Wi-Fi, «слишком свежий», свободное имя, переименования
  sync/Uploader.kt  заливка одного файла: presigned-части в S3 либо чанки через сервер
  sync/UploadEngine.kt проход: скан → дедуп → переносы → очередь → выгрузка
  sync/Downloader.kt скачивание с докачкой и проверкой (открытие файла из браузера)
  sync/MediaCleanup.kt чистка медиатеки после удаления файла пользователем
  docs/CloudlyDocumentsProvider.kt файловый браузер для системы
  ui/               главный экран, выбор папок, «Поделиться», «Освободить место»
  work/             периодический воркер, короткий dataSync-сервис, уведомления
```

Проход автозагрузки: обход папки задачи → сравнение с кэшем → хэш нового и изменённого →
`/sync/have` одним батчем → переименования по совпадению содержимого (move) → остальное в очередь
(`ops`) → заливка очереди с ретраями (30 с, 2 мин, 10 мин, 1 ч, далее раз в 6 часов).

Заливка: части по presigned-ссылкам прямо в S3 (параллельно 3 части, 2 при файле >1 ГБ),
продолжение с последней принятой части после обрыва. Если хранилище с телефона недоступно (DNS,
блокировщик, VPN) — переключение на relay через сервер и запоминание режима; в интерфейсе видно
предупреждение и кнопка возврата к прямой загрузке.

Фон: периодическая задача WorkManager раз в 15 минут (переживает перезагрузку) + запуск после
добавления папки; короткий `dataSync`-сервис только на время активной передачи («Синхронизировать
сейчас») с прогрессом, кнопкой «Стоп» и обработкой лимита Android 15 (6 часов в сутки).

## Файловый браузер (DocumentsProvider)

- Authority `ru.cloudly.sync.documents`; корень — корневая папка владельца, id документа папки —
  её uuid, файла — `f:uuid`.
- Чтение: `queryChildDocuments` (папки, затем файлы, сортировка по имени), `queryDocument`,
  `queryRecentDocuments` (раздел «Последние»), пагинация `children` соблюдается.
- Открытие файла: скачиваем в кэш `cacheDir/browse` с докачкой и проверкой размера и `sha256`,
  отдаём обычный seekable `ParcelFileDescriptor` (pipe без перемотки ломает часть просмотрщиков).
  Кэш ограничен 1 ГБ, чистится по времени последнего использования.
- Миниатюры: `/previews/:sha?w=512` (для больших запросов — 2048), оригинал не качается.
- Запись: `createDocument` заводит папку сразу на сервере; для файла запоминается место, а
  `openDocument(..., "w")` отдаёт дескриптор на временный файл через `openProxyFileDescriptor`.
  Закрытие дескриптора (`onRelease`) — момент, когда файл дописан: выгружаем в ту папку, где
  пользователь его создал (свободное имя, relay при недоступности S3). Если выгрузка не удалась,
  файл остаётся на телефоне, а в уведомлении указан его путь — молча терять пользовательское
  сохранение нельзя.
- Переименование и удаление поддержаны; удаление — корзина сервера, файлы на телефоне не трогаются.
  Правка содержимого облачного файла не поддерживается (только чтение).

## Правила корректности (действуют)

- Один проход за раз: периодический воркер и «Синхронизировать сейчас» — разные исполнители,
  без лока два движка заливали бы одни файлы и качали в один временный файл (`App.tryEnterSync`).
- Имя из внешнего источника (система «Поделиться», файловый браузер) очищается от пути, «..»
  и управляющих символов и ограничивается по длине (`Decisions.cleanFileName`) — иначе
  `../../databases/app.db` записался бы или удалился файл вне каталога приложения.
- Файл, изменённый только что (30 с), берётся следующим проходом: он может ещё дописываться.
- Дата из будущего не считается «слишком свежей» — иначе файл не выгрузился бы никогда.
- Нечитаемая папка не превращается в пустую: в интерфейсе видно «папка не читается», а не
  молчаливый ноль.
- Скачанное для открытия проверяется по размеру и хэшу; битая закачка не попадает в кэш как файл.
- Ошибки называют виновника: «S3-хост: unable to resolve host», «сервер не ответил», «нет доступа
  (проверь токен)» — вместо «unable to resolve host no addreass associated with this host».
- Сессия загрузки, на которой упала первая попытка, прерывается (`abort`), иначе на сервере
  копились бы брошенные сессии и упирались в лимит `MAX_UPLOAD_SESSIONS_PER_USER`.
- SQLite не читается в главном потоке.

## Серверный контракт (M3.0 — сделано)

Изначальный список доработок (оставлен как история решений):

1. Журнал изменений (append-only `seq`) + tombstones, живущие дольше записи.
2. `clientMtime` + `updatedAt` у `FileEntry`.
3. `keepOffline` у `Folder` и `FileEntry` + ручки правки из веба.
4. `PATCH /files/:id {folderId, name, keepOffline}` — переноса файла в REST не было вообще.
5. `replace` в `init`/`complete` (был `409` из-за `@@unique([folderId, name])`).
6. GC осиротевших `Asset` и их `view/*` при перезаписи.
7. Bearer-токен в REST (`AuthGuard` умел только cookie).
8. `POST /sync/have` (батч sha → что уже есть).
9. `POST /folders/ensure-path` (идемпотентный mkdir).
10. Лимит активных `UploadSession` на пользователя.

Авторизация: `Authorization: Bearer <ApiToken>` (тот же app-password, что и Basic в WebDAV).
Токен со scope `files:ro` пускается только на GET/HEAD/OPTIONS, на запись — 403.

**Что использует клиент сейчас:** `POST /sync/have`, `POST /folders/ensure-path`,
`GET /folders/:id/children` (пагинация `?after=`), `GET /folders/:id/meta`, `GET /files/:id`,
`GET /files/:id/content` (Range), `PATCH /files/:id`, `DELETE /files/:id`,
`PATCH /folders/:id`, `DELETE /folders/:id`, `GET /previews/:sha?w=`, `POST /uploads`,
`GET /uploads/:id`, `POST /uploads/:id/url/:part`, `PUT /uploads/:id/parts/:part`,
`PUT /uploads/:id/chunks/:part`, `POST /uploads/:id/complete`, `DELETE /uploads/:id`,
`POST /auth/login`, `POST /auth/tokens`, `DELETE /auth/tokens/:id`.

**Лента изменений** (серверная, клиентом не используется):
`GET /api/v1/sync/changes?since=<seq>&limit=<≤500>`

```json
{ "since": "3", "nextSeq": "6", "hasMore": false, "minSeq": "1", "resetRequired": false,
  "changes": [ { "seq": "4", "target": "folder|entry", "op": "create|update|move|delete|restore|pin",
                 "targetId": "…", "folderId": "…", "name": "…", "zone": "FILES|PHOTOS",
                 "sha256": "…|null", "size": 123|null, "mime": "…", "clientMtime": "ISO|null",
                 "keepOffline": false, "at": "ISO" } ] }
```

- Курсор — `seq` (монотонный), не `updatedAt`. `resetRequired: true` — курсор старше самого старого
  события (журнал чистили), нужен полный рескан.
- `op: delete` у папки означает «удалено всё поддерево» — отдельные события по детям не пишутся.
- `GET /folders/:id/children` отдаёт содержимое порциями `{ hasMore, nextAfter, folders, entries }`:
  клиент обязан ходить по страницам, иначе большая папка придёт не целиком.

**Загрузка.** `POST /api/v1/uploads` принимает `replace`, `clientMtime`, `expectedSha256`,
`expectedUpdatedAt` (предполётное условие перезаписи, нужен `replace: true`) и `mode: direct|relay`.
Лимит одновременных незавершённых загрузок — `MAX_UPLOAD_SESSIONS_PER_USER` (16): брошенные сессии
(>15 минут, ни одной части) сначала подчищаются, потом вытесняется самая старая; иначе телефон
однажды заблокировал бы себе все загрузки ответом `429`. Повторный `complete` идемпотентен.

**Миграция.** `prisma migrate deploy` → `20260910184610_sync_changelog_keepoffline`
(таблица `ChangeLog`, `FileEntry.updatedAt/clientMtime/keepOffline`, `Folder.keepOffline`,
`UploadSession.replace/clientMtime/completedAt/result/expectedSha256/expectedUpdatedAt`).

**Проверено на локальной Postgres:** миграция на непустой таблице (backfill), цепочка
`migrate deploy` с нуля, каждая ручка (curl), журнал по create/update/pin/delete, tombstone после
`trash purge`, отказ read-only токена, лимит сессий с очисткой зависших, `replace` с сохранением id
и удалением осиротевшего ассета. Отдельно — `scripts/m3-sync-check.mjs`: контрактные проверки на
чистой БД без S3.

## Сборка, поставка, проверка

```bash
cd android
JAVA_HOME=/opt/homebrew/opt/openjdk@21 ./gradlew :app:testDebugUnitTest :app:assembleRelease
```

Релиз подписывается ключом `~/.cloudly-android-release.jks` через `android/keystore.properties`
(в git не попадает), после R8 — около 2,8 МБ. Готовый APK публикуется в облако владельца
(`scripts/publish-apk.mjs` → папка `apk`, файл `cloudlyru-sync.apk`); обновление заменяет файл,
ссылка `/api/v1/files/<entryId>/content` не меняется. GitHub Actions собирает серверную часть,
Android собирается локально на маке (CI для Android нет).

## Отложено

- **iOS** — только для справки, приложения нет. Возможно: автозагрузка фото (`PHPhotoLibrary`),
  выбранная через «Файлы» папка, Share Extension. Невозможно: полный доступ к файловой системе,
  постоянный фоновый сервис, автоматическое удаление фото; поставка только через Xcode/TestFlight,
  99 долларов в год.
- **Двусторонняя синхронизация, срок хранения на телефоне, «держать офлайн»** — снято вместе с
  зеркальной моделью. Журнал изменений и `keepOffline` на сервере остались: они нужны вебу и
  пригодятся, если двустороннюю модель когда-нибудь вернут.
- Мелочи, которых нет: `keepMinFreeGb`, фильтры (только медиа, минимальный размер, исключения имён),
  «заряжается» в условиях задачи, автоочистка корзины сервера, retention журнала.
