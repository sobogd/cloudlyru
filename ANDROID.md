# CloudlyRu Android — план мобильного клиента

Статус: решения согласованы, код не начат. Дополняет `PLAN.md` (§16, этап M3).

## Цель

Служебное приложение, которое живёт на телефоне и синхронизирует выбранные папки в облако.
Пользователь выбирает: какую папку синхронизировать и в какую зону она льётся — «Фото»
(превью, таймлайн, EXIF) или «Файлы» (как есть). Плюс управление местом на телефоне:
автоудаление выгруженного по сроку и закрепление «держать офлайн».

## Решения (зафиксировано)

- **Только Android, только APK, sideload.** В Google Play не идём, flavor'ов нет.
- **Доступ к файлам: `MANAGE_EXTERNAL_STORAGE`** («Доступ ко всем файлам»). SAF не используем:
  обычные пути, быстрый скан, `FileObserver`, `setLastModified`, доступен корень `Download/`.
- **Сервер — мастер-копия, телефон — реплика.** Удаления сходятся к «удалено» с обеих сторон;
  точка восстановления одна — корзина сервера (`TRASH_RETENTION_DAYS`, по умолчанию 30 дней).
- **Фото: заливка односторонняя, удаления двусторонние.** Альбомов нет ни в UI, ни в API; EXIF и
  превью делает сервер; докачки фото с сервера нет (кроме закреплённых). Удаление фото на телефоне
  уносит запись в корзину сервера.
- **Файлы: подпапки выбранной папки зеркалятся как есть**, вместе с пустыми каталогами.
- **Фото: плоско.** Все файлы задачи ложатся прямо в целевую папку: структура подпапок телефона не
  переносится, по датам ничего не раскладывается. Нужны разные места — это отдельные задачи. Если два
  разных файла претендуют на одно имя: одинаковый `sha256` — это одна запись, разный — имя занимает
  синхронизировавшийся первым, второй получает суффикс (`IMG_0001 (2).jpg`).
- **Зона — следствие целевой папки**, а не отдельная сущность.
- **Вложенные задачи:** подпапка с другими правилами — отдельная задача, родительская её поддерево
  исключает; выигрывает самая глубокая задача (самый длинный путь).
- Идентичность файла — `sha256`. `mtime` — только дешёвый предфильтр, не истина.

## Модель задачи

```
SyncJob {
  sourceDir        // абсолютный путь на телефоне
  targetFolderId   // папка на сервере
  zone             // PHOTOS | FILES (следствие targetFolder)
  includeSubfolders // в «Файлах» сохраняет структуру, в «Фото» просто обходит и раскладывает плоско
  filters          // только медиа / всё, min size, исключения имён
  constraints      // wifi-only, charging-only
  deletion         // trash-on-server | never
  keepDays         // по умолчанию «не удалять» (зеркало); 0 = сразу после выгрузки
  keepMinFreeGb    // не чистить, пока свободно больше X
}
```

UI: «Добавить папку» → выбрать каталог → «Фото» или «Файлы» → выбрать/создать папку на сервере →
настроить срок хранения.

## Три режима папки

| Режим | Вверх | Вниз | Автоудаление на телефоне |
|---|---|---|---|
| Кэш (`keepDays > 0`) | да | нет | по таймеру |
| Зеркало (`keepDays = не удалять`) | да | да | нет |
| Офлайн (флаг с сервера) | да | да, всё | нет, принудительно |

В папке-кэше скачивание запрещено, **но удаления с сервера применяются**: иначе удалённый в вебе
файл останется на телефоне и при первом же локальном изменении зальётся обратно.

## Закрепление «держать офлайн»

- Флаг живёт **на сервере**: `keepOffline` у `Folder` и у `FileEntry`. Ставится из веба.
- Перекрывает `keepDays`. Действие двойное: (1) вытеснение выключено; (2) отсутствующие локально
  файлы докачиваются — иначе «офлайн» врёт.
- Включение флага = массовая докачка: видимый прогресс, пауза, отмена, приоритет wifi, докачка
  после обрыва.
- Перед закреплением показываем «в папке X ГБ, свободно Y». Если места не хватает — **закреплённое
  не вытесняется никогда молча**: ошибка и предложение снять флаг.
- Флаг доезжает до телефона как событие журнала изменений (в том числе после офлайна).
- **Удаления флаг не отменяет:** закреплённый файл, удалённый на сервере, удаляется и на телефоне.

## Автоудаление выгруженного (retention)

- Срок считается **от времени успешной загрузки**, не от `mtime` файла.
- Удаляем только после подтверждения сервером **того же sha и размера** (и что объект реально в S3).
- Незагруженное не удаляется никогда; месяц офлайна = файлы копятся, чистки нет.
- `keepDays = 0` — грейс 5–10 минут после завершения записи, плюс пропуск файлов, которые ещё
  меняются (`mtime` младше ~30 с).
- Удаление **настоящее** (место освобождается сразу, откат — скачать из веба). Для медиа нельзя
  просто `File.delete()`: удаляем через `ContentResolver.delete()` по URI (строка MediaStore уходит
  вместе с файлом), иначе в галерее останутся битые превью.
- Системной корзиной медиа («Недавно удалённые») не управляем вообще: файл удаляется сразу и
  по-настоящему, телефонная корзина сама себя чистит. Единственная точка отката — корзина сервера.
- Локальное состояние становится тройным: `синхронизирован` | `вытеснен нами` | `ещё не выгружен`.
  Без флага «вытеснен» зеркало будет скачивать обратно, а retention — удалять серверные копии.
- **Вытеснение ≠ удаление.** Вытеснение только локальное: серверная копия остаётся, запись в дереве
  живёт, у неё просто помечено `вытеснен`. Удаление (пользователем или на сервере) — событие для
  обеих сторон и запись в корзине сервера. Перепутать их = retention уничтожит облако, а удаление
  на телефоне сойдёт за экономию места.
- Локальные файлы вне `base` (никогда не выгружались) в сверке не участвуют и в интерфейсе
  не показываются как проблема — только счётчик прогресса.
- История вытеснений и режим «показать, что будет удалено» (dry-run), счётчики «на телефоне X ГБ,
  освобождено Y ГБ».

## Семантика по событиям

| Событие | Фото | Файлы |
|---|---|---|
| новый/изменённый файл на телефоне | заливаем; изменённый — replace | заливаем; replace, если сервер не менялся |
| файл создан/изменён на сервере | игнорируем | скачиваем (в папке-кэше — игнорируем) |
| удалил на телефоне | запись на сервере → в корзину | запись на сервере → в корзину |
| удалили на сервере | удаляем и на телефоне | удаляем и на телефоне (в кэше — тоже) |
| удалил локально, а серверная версия новее | — | конфликт-копия вверх, канон на сервере не перезаписываем |
| переименование/перенос | детект пары sha → move | детект пары sha → move |

## Правила корректности

1. Три стороны: локальное состояние, серверное и `base` (что видели в прошлый раз) — в Room.
2. Удаление распознаётся только по `base`: «было в base, локально исчезло» = удаление.
3. Сервер отдаёт журнал изменений с монотонным `seq` и tombstones: `create`, `update`, `move`,
   `delete`, `restore`, `pin`. Курсор — `seq`, не `updatedAt`. Tombstone применяется один раз.
4. `restore` из корзины (в пределах `TRASH_RETENTION_DAYS`) — обычное событие: если в задаче
   разрешена докачка, файл возвращается и на телефон (в закреплённой папке — обязательно; в фото-
   и кэш-папках восстанавливается только в облаке).
5. Переименование/перенос: детект пары (тот же sha, одна запись исчезла, другая появилась) →
   `move` на сервере. При неоднозначности — удаление + создание.
6. Перезапись: `replace` в `init`/`complete`, id записи не меняется.
7. Конфликт (обе стороны изменились): каноническое имя занимает серверная версия (истина — сервер),
   локальная сохраняется как `имя (конфликт, <устройство>, YYYY-MM-DD).ext` и заливается.
8. Атомарность: `.tmp` рядом с целью → `rename`.
9. `mtime` сервера применяется к скачанному файлу (`setLastModified`), чтобы скан не видел ложное
   изменение (в папке-кэше неактуально — там скачивания нет).
10. Заливка: `init(sha256)` → `deduped: true` (байты не идут) либо direct-части в S3 → `parts` →
    `complete`. Часть `max(8 МБ, size/9000)`, параллелизм 2–3, бэкофф, очередь в БД.
11. Первый синк: полный скан + хэширование + батч `/sync/have` → заливаются только отсутствующие.
12. **Аварийный стоп:** если корень задачи недоступен или скан аномален (папка пропала, карта не
    смонтирована, прав нет, было 5000 файлов — стало 0) — проход прерывается с ошибкой, никаких
    удалений. Плюс предохранитель на массовое удаление: если проход хочет удалить больше 20 файлов
    или больше 10 % того, что в `base`, — стоп, показать список и спросить.
13. Исключения по умолчанию: `Android/data`, `Android/obb`, `.thumbnails`,
    `.trashed`, `LOST.DIR`, `*.tmp`, `.DS_Store`.
14. Фон: WorkManager (периодика + expedited по событию) как основной движок, `dataSync`-FGS только
    на время активной передачи (Android 15: лимит 6 ч за 24 ч, из `BOOT_COMPLETED` не стартует).
    Плюс просьба отключить оптимизацию батареи.
15. Раз в неделю — сверка (re-hash выборки на wifi) и экран «конфликты / не ушло / не пришло».
16. Интерфейс «требует внимания» — только конфликты и ошибки, не очередь выгрузки.

## Что добавить на сервере (M3.0) — сделано

Изначальный список (оставлен как история решений):

1. Журнал изменений (append-only `seq`) + tombstones, живущие дольше записи: раньше `trash purge`
   физически удалял строки и клиент залил бы удалённое заново.
2. `clientMtime` + `updatedAt` у `FileEntry`.
3. `keepOffline` у `Folder` и `FileEntry` + ручки правки из веба (событие в журнале).
4. `PATCH /files/:id {folderId, name, keepOffline}` — в REST переноса файла не было вообще
   (DAV `MOVE` умеет только переименование внутри той же папки).
5. `replace` в `init`/`complete` (был `409` из-за `@@unique([folderId, name])`).
6. GC осиротевших `Asset` и их `view/*` при перезаписи.
7. Bearer-токен в REST (`AuthGuard` умел только cookie).
8. `POST /sync/have` (батч sha → что уже есть).
9. `POST /folders/ensure-path` (идемпотентный mkdir).
10. Лимит активных `UploadSession` на пользователя.

Контракт целиком — в разделе «M3.0 — сделано» ниже.

## M3.0 — сделано (серверный контракт для клиента)

### Правки после ревью (все находки закрыты)

- **Блокер:** `replace` и `clientMtime` не пробрасывались из HTTP в сервис загрузки — перезапись
  была недоступна по API (всегда 409). Теперь поля контракта `POST /uploads` работают.
- **Падение процесса:** `gcOrphanAsset` вызывался «в пустоту» без `.catch` — сбой БД в момент
  перезаписи убивал API (unhandled rejection в Node 22). Теперь GC ждётся и логирует ошибки.
- **Удаление живых данных:** GC и `trash purge` сначала удаляют строки `Asset` под условием
  «ссылок нет» (в одной транзакции с tombstone'ами) и только потом трогают объекты S3, перепроверив,
  что строка с тем же sha не появилась снова. Раньше параллельный дедуп-upload мог потерять байты.
- **Перенос в «Фото»** через `PATCH /files/:id` теперь запускает EXIF и очередь превью — без этого
  файл попадал в медиа-зону без метаданных и не был виден в таймлайне.
- **Безопасность:** выпуск/отзыв токенов и безвозвратная очистка корзины — только веб-сессия
  (`@SessionOnly`); кап на живые токены (32) и аудит выдачи/отзыва; `olderThanDays` клампится,
  отрицательное значение больше не означает «вычистить всё»; `POST /sync/have` разрешён
  read-only токенам (`@ReadOnlyAllowed`).
- **Журнал надёжнее:** событие пишется в одной транзакции с мутацией (`tx` пробрасывается), а не
  отдельным запросом после; восстановление папки пишет события и по детям (`restore`), иначе
  поддерево из журнала не восстановить; в распаковке архивов ошибки журнала больше не глушатся,
  а создание записей идёт через `FilesService.createEntry`.
- **Корзина:** `replace` не воскрешает удалённое (409) — WebDAV-клиенты (Finder/rclone) получают
  прежнее поведение через явный флаг `restoreDeleted`, клиент синхронизации — нет.
- **Идемпотентность `complete`:** сессия не удаляется сразу, ответ сохраняется
  (`UploadSession.completedAt` + `result`), повторный `complete` возвращает тот же результат.
- **Курсор:** `resetRequired` срабатывает и на пустом журнале, и когда курсор впереди журнала
  (БД восстановили из бэкапа) — иначе клиент залипал навсегда; `since` вне BIGINT не роняет запрос.
- **`/sync/have`:** считает только живое дерево (запись не в корзине, папка не удалена) — иначе
  клиент пропускал заливку и после retention терял данные.
- **Прочее:** лимиты `ensure-path` (32 сегмента, 1024 символа), внятные 409 вместо 500 на гонках
  уникальных имён, `isPlainObject` в новых ручках, зарезервированное имя `__root__` (иначе папка
  становится неуправляемой), защита от циклов в обходе дерева, реальный размер файла в DAV PUT
  (при `Transfer-Encoding: chunked` писался 0 и утекал в журнал), поиск владельца дерева одним
  рекурсивным запросом вместо лимита в 64 уровня.
- **Регрессионная проверка:** `scripts/m3-sync-check.mjs` — 40+ проверок контракта на локальной БД
  без S3: перезапись и GC, журнал (create/update/move/pin/delete/restore), tombstones после корзины,
  курсор и `resetRequired`, `/sync/have`, проброс `replace`/`clientMtime` через HTTP-контроллер.
  Запуск: `DATABASE_URL=… SESSION_SECRET=… ADMIN_LOGIN=admin ADMIN_PASSWORD=admin node scripts/m3-sync-check.mjs`

### Решения по открытым вопросам (закрыты)

1. **Retention журнала `ChangeLog` — оставляем как есть.** Лента растёт вечно, но это одна маленькая
   строка на изменение. Если таблица когда-нибудь станет заметной, включаем подрезку: клиент уже
   готов — `resetRequired` срабатывает на курсор старше самого старого события.
2. **Оптимистичная блокировка перезаписи — сделана.** `POST /uploads` принимает `expectedSha256`
   и/или `expectedUpdatedAt` (требуют `replace: true`). Проверка идёт **до начала загрузки**:
   расхождение версий → 409 `stale_version` со снимком фактической версии (sha, размер, mime,
   clientMtime, updatedAt) — клиент сразу делает конфликтную копию и не тратит трафик.
   Та же проверка повторяется на `complete`/`createEntry` — между init и complete версия могла
   измениться. Без предусловия поведение прежнее (веб-форма, WebDAV, скрипты).
3. **`keepOffline` из веба — сделано.** В деталке файла и папки появилась кнопка 📌: ставит и снимает
   флаг через `PATCH /files/:id` и `PATCH /folders/:id`, состояние показывается в метаданных папки.

### Превью для фото: где считать (на проработку)

Сейчас считает сервер: для зоны «Фото» `queue.enqueue` делает `view/<sha>-512.webp` (сетка),
`view/<sha>-2048.avif` (полный экран), для видео — постер и `view/<sha>-1080.mp4`. Ключи привязаны
к sha оригинала, поэтому источник превью схему не меняет: кто бы ни посчитал файл, ключ один.

- **Только сервер (текущий вариант).** Единообразно для телефона, веба и Mac, одно место правды,
  превью можно пересобрать. Минус: VPS на два ядра, AVIF/AV1 дорогие, первая выгрузка библиотеки
  в тысячи фото считается часами.
- **Только телефон.** Экономит CPU сервера, но качество и ориентация разъезжаются между
  устройствами и версиями Android, нужно доверять клиенту (подсунутое «превью» попадёт в галерею),
  и загрузки из веба/с других устройств всё равно требуют серверного пути. Как единственный — нет.
- **Гибрид (если замеры покажут, что сервер не тянет).** Телефон присылает превью вместе с
  оригиналом как «быстрый путь», сервер его проверяет (mime из белого списка, размеры, размер файла,
  декодирование заголовка; при несоответствии — в обычную очередь) и всегда может перегенерировать.
  Плюс — первая выгрузка ускоряется в разы, минус — ещё одна ветка загрузки и путь деградации.

Рекомендация: начать с серверного варианта (он уже работает), замерить первую выгрузку на реальной
библиотеке и включать гибрид только если это станет болью. Независимо от этого приложение показывает
локальные превью для файлов, которые ещё лежат на устройстве, — это чисто клиентская оптимизация.

Авторизация: `Authorization: Bearer <ApiToken>` (тот же app-password, что и Basic в WebDAV).
Токен со scope `files:ro` пускается только на GET/HEAD/OPTIONS, на запись — 403.

**Лента изменений.** `GET /api/v1/sync/changes?since=<seq>&limit=<≤500>`

```json
{ "since": "3", "nextSeq": "6", "hasMore": false, "minSeq": "1", "resetRequired": false,
  "changes": [ { "seq": "4", "target": "folder|entry", "op": "create|update|move|delete|restore|pin",
                 "targetId": "…", "folderId": "…", "name": "…", "zone": "FILES|PHOTOS",
                 "sha256": "…|null", "size": 123|null, "mime": "…", "clientMtime": "ISO|null",
                 "keepOffline": false, "at": "ISO" } ] }
```

- Курсор — `seq` (монотонный), не `updatedAt`. Сохранять `nextSeq`; при `hasMore: true` запрашивать снова.
- `resetRequired: true` — курсор старше самого старого события (журнал чистили): нужен полный рескан.
- Каждая строка — снимок цели, клиенту достаточно применить её по порядку; внешних ключей нет,
  поэтому tombstone (`op: delete`) переживает физическое удаление записи из БД.
- `op: delete` у папки означает «удалено всё поддерево» — отдельные события по детям не пишутся.
- Журнал не покрывает: создание системных корней (`__root__`, «Фото») и смену зоны поддерева —
  это клиенту не нужно (дерево он видит через `/folders`, зону решает сервер по папке-приёмнику).
- Хвост: если хранить журнал вечно станет дорого, добавим retention и тогда `resetRequired`
  начнёт срабатывать штатно (клиент это уже умеет).

**Что уже есть.** `POST /api/v1/sync/have { sha256: [...] }` (≤500) →
`{ present: [{ sha256, size, mime }] }` — только своё содержимое; нужен на первом скане,
чтобы не слать `init` на каждый файл.

**Папки.**
- `POST /api/v1/folders/ensure-path { path: "Files/2025/07", parentId? }` → `{ id, name, parentId, zone, created }`
  — идемпотентный mkdir, отсутствующие сегменты создаются, занятые корзиной → 409.
- `PATCH /api/v1/folders/:id { name?, parentId?, keepOffline? }` — переименование, переезд,
  «держать офлайн» (флаг перекрывает вытеснение на клиенте).

**Файлы.** `PATCH /api/v1/files/:id { name?, folderId?, keepOffline?, clientMtime? }` — перенос
отдельной операцией (id записи сохраняется, в журнал уходит `move`, а не «удали + создай»).

**Загрузка.** `POST /api/v1/uploads` принимает дополнительно `replace: boolean`, `clientMtime: ISO`
(ответ содержит `replaced`), `expectedSha256` и `expectedUpdatedAt` — предполётное условие
перезаписи (нужен `replace: true`). Перезапись сохраняет id записи; прежнее содержимое, оставшееся
без ссылок, сразу убирается из S3 вместе с `view/*`. Лимит одновременных незавершённых загрузок —
`MAX_UPLOAD_SESSIONS_PER_USER` (по умолчанию 16), при превышении 429, брошенные сессии при этом
сначала подчищаются. Повторный `complete` возвращает сохранённый ответ (сессия живёт ещё час).

**Миграция.** `prisma migrate deploy` → `20260910184610_sync_changelog_keepoffline`
(таблица `ChangeLog`, `FileEntry.updatedAt/clientMtime/keepOffline`, `Folder.keepOffline`,
`UploadSession.replace/clientMtime`). Для существующих строк `updatedAt` заполняется из `createdAt`.

**Что проверено на локальной Postgres:** миграция на непустой таблице (backfill), вся цепочка
`migrate deploy` с нуля, каждая ручка выше (curl), journал по create/update/pin/delete, tombstone
после `trash purge`, отказ read-only токена, лимит сессий с очисткой зависших, `replace` с
сохранением id и удалением осиротевшего ассета (9 ключей S3: оригинал + производные).
