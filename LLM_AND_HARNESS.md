# LLM и харнесс: как они устроены, как связаны с железом и как работают вместе

Что внутри этого текста: сначала — что такое LLM физически и математически, потом — как из
этого получается генерация текста, дальше — что означают все параметры (и модели, и генерации),
потом — почему всё упирается в память видеокарты, и в конце — что такое харнесс, из чего он
состоит и как он разговаривает с моделью. Примеры харнесса — реальные: это DSH, в котором ты
сейчас читаешь этот ответ.

---

## 1. Самое короткое изложение

**LLM** — это файл с числами (весами) плюс код, который эти числа применяет. На вход — последовательность
чисел (токенов), на выход — вероятности для следующего токена. Больше она не делает ничего.

**Харнесс** — обычная программа на компьютере, которая: собирает для модели входной текст, отправляет
его по сети, получает ответ, исполняет то, что модель попросила (прочитать файл, запустить команду,
сходить в интернет), приклеивает результат обратно к тексту и повторяет это в цикле, пока задача не
закончится.

Одна фраза, которая объясняет всю разницу: **модель предлагает, харнесс делает**. Модель физически
не может ничего выполнить — у неё нет ни доступа к диску, ни к сети, ни даже памяти о предыдущем
запросе. Всё, что выглядит как «агент работает», — это цикл в харнессе плюс текст, который модель
породила.

## 2. Что такое LLM на самом деле

### 2.1 Формально

LLM — это функция:

```
текст на входе  ->  вероятности для следующего кусочка текста на выходе
```

Всё. Никакого «понимания», «базы знаний» и «планирования» в архитектуре нет. Есть огромная таблица
чисел (весов) и арифметика над ними. Всё остальное поведение — побочный эффект того, что эта функция
хорошо предсказывает продолжение текста.

Пример: на вход подали `Столица Франции —` и получили словарь вида
`Париж: 0.94, Лион: 0.02, ...`. Харнесс (или код рядом) выбирает один вариант, приклеивает его к
тексту и запускает функцию снова. Так порождается текст — по одному куску за раз.

### 2.2 Физически

Модель на диске — это один большой файл (или несколько шардов) с числами в формате float или
целых. Например, модель на 70 миллиардов параметров в 16-битном формате занимает около 140 ГБ.
Внутри нет ни строк, ни правил, ни «факта, что Париж — столица Франции». Есть 70 миллиардов чисел,
подобранных обучением так, чтобы предсказание работало.

Отсюда два следствия, о которые спотыкаются почти все:

- **Модель не хранит знания в явном виде.** Нельзя «заглянуть в базу» и найти там факт. Знание
  размазано по числам, поэтому модель может уверенно сказать чушь — у неё нет механизма проверки.
- **Модель не обновляется от разговора.** Проговорили вы с ней что-то — веса не изменились.
  Единственная «память» — это текст, который харнесс положит в следующий запрос.

### 2.3 Что модель умеет и что не умеет по своей природе

| Умеет (по природе) | Не умеет (никогда, без харнесса) |
|---|---|
| Продолжать текст правдоподобно и по стилю | Помнить предыдущий запрос |
| Переформулировать, переводить, суммировать | Читать и писать файлы |
| Порождать код и структурированный текст (JSON) | Запускать команды и видеть их вывод |
| «Рассуждать» по шагам, если её так обучили | Знать сегодняшнюю дату, курс, погоду |
| Следовать инструкциям в промпте | Проверять факты или считать точно |
| Выдавать «вызов инструмента» как текст | Выполнять этот вызов |

Правая колонка — это ровно тот список, которым занимается харнесс.

## 3. Токены: почему модель видит не буквы

Модель не работает с текстом. Она работает с **токенами** — кусочками текста из заранее
заготовленного словаря (обычно 50–200 тысяч единиц). Русское слово «привет» может быть одним
токеном, а «синхронизировать» — четырьмя. Английское `the` — почти всегда один токен, эмодзи или
редкий символ — иногда три.

Как получается словарь: берут много текста и статистически ищут часто встречающиеся куски
(алгоритм BPE — byte pair encoding). Частые слова и куски слов становятся отдельными токенами,
редкие разбираются на части. Поэтому:

- в английском один токен ≈ 4 символа;
- в русском один токен ≈ 2–3 символа, кириллица дороже латиницы примерно в 1.5–2 раза;
- числа и код разбираются на куски непредсказуемо (`1234567` может стать `123` + `4567`), и
  именно поэтому модели плохо считают в столбик — они видят не цифры, а куски;
- пробелы и регистр «приклеены» к токенам: ` файл`, ` Файл`, `Файл` — три разных токена.

Практические последствия, которые важнее теории:

1. **Контекст измеряется в токенах, а не в символах или страницах.** «Окно 128k» — это примерно
   400–500 тысяч символов английского текста и вдвое меньше русского.
2. **Цена запроса** считается по токенам, и русский текст выходит дороже английского при том же
   смысле.
3. **Разные модели режут текст по-разному.** Нельзя сравнивать «токены» двух моделей напрямую —
   словари у них разные.
4. **Специальные токены** (`<|im_start|>`, `<|end_of_text|>` и подобные) служебные: ими размечены
   роли в диалоге. Их подставляет харнесс, а не человек, — обычно через «chat template», шаблон
   сборки диалога в одну строку.

## 4. Как модель устроена внутри (трансформер-декодер)

Простыми словами: это стопка одинаковых блоков (обычно 30–100 штук), через которые токены
проходят по очереди. Каждый блок делает две вещи: даёт токенам «посмотреть друг на друга»
(attention) и «подумать над каждым по отдельности» (MLP). Всё остальное — обвязка.

### 4.1 Путь одного запроса по слоям

1. **Токенизация.** Текст → список целых чисел (id токенов).
2. **Эмбеддинги.** Каждый id превращается в вектор чисел (например, 4096 чисел). По смыслу это
   «координаты токена в пространстве смыслов». Похожие по употреблению токены оказываются рядом.
3. **N слоёв трансформера.** В каждом:
   - **Attention.** Каждый токен формирует три вектора: Query («что я ищу»), Key («что я могу
     предложить») и Value («что у меня есть»). Токен сравнивает свой Query со всеми Key предыдущих
     токенов, получает веса важности и смешивает их Value. Так слово «оно» подтягивает смысл
     существительного из начала фразы.
     Важная деталь: в генеративных моделях стоит **causal mask** — токен видит только предыдущие
     токены, не будущие. Иначе предсказание следующего токена стало бы подглядыванием.
   - **Несколько голов.** Attention считается параллельно несколькими «головами» (heads), каждая
     ловит свою разновидность связи: синтаксис, повторы, дальние отсылки, пунктуацию. Потом
     результаты склеиваются.
   - **MLP (feed-forward).** Двухслойная сеть, которая применяется к каждому токену независимо.
     Здесь живёт основная масса параметров — обычно около двух третей. Грубо это «память фактов и
     шаблонов», тогда как attention отвечает за связи между токенами.
   - **Остаточные связи (residual) и нормализация.** Вход слоя прибавляется к его выходу. Без
     этого градиенты при обучении глубоких сетей затухают, и ничего глубже десятка слоёв не
     обучается. Нормализация держит числа в разумном диапазоне.
4. **Позиции.** Вниманию всё равно, в каком порядке шли токены, поэтому позиция добавляется
   отдельно (современный способ — RoPE, вращение векторов на угол, зависящий от позиции). Отсюда
   же растут трюки с растягиванием контекста.
5. **Финальная проекция.** Выход последнего слоя умножается на матрицу размера «скрытый размер ×
   размер словаря» и превращается в баллы (logits) для каждого токена словаря.
6. **Softmax.** Баллы → вероятности. Всё, функция выдала распределение.

Число параметров — это в основном сумма размеров всех этих матриц. Отсюда обозначения `8B`, `70B`,
`671B`: миллиарды чисел.

### 4.2 Как это обучают

Обучение — это подгонка чисел так, чтобы предсказание совпадало с реальным текстом.

- **Предобучение.** Берут триллионы токенов текста, показывают модели кусок, просят предсказать
  следующий токен, сравнивают с настоящим (функция потерь — cross-entropy), и сдвигают веса
  алгоритмом обратного распространения (backprop) с оптимизатором вроде AdamW. Повторяют
  квадриллионы раз. Здесь модель получает язык, факты и «мир» из текста.
  Ориентир по объёму данных: около 20 токенов на каждый параметр (правило Chinchilla), у крупных
  современных моделей — заметно больше.
- **Дообучение на инструкциях (SFT).** Те же шаги, но на парах «инструкция → хороший ответ»,
  написанных людьми. Здесь модель из «продолжателя текста» становится «помощником».
- **Выравнивание (RLHF / DPO / RLVR).** Люди (или автоматические проверки) оценивают ответы, и
  модель подстраивают под эти оценки. Отсюда берутся вежливый тон, отказы на опасные просьбы,
  склонность к формату «сначала план, потом действие» и стиль рассуждений у reasoning-моделей.

Что здесь важно понять: **ни один этап не добавляет модель возможность что-то выполнить**. Даже
самая обученная модель остаётся функцией «текст → вероятности».

### 4.3 Почему модель галлюцинирует

Потому что она оптимизирована на правдоподобие, а не на истину. Если в обучающих данных про
несуществующую библиотеку написано правдоподобно, модель продолжит в том же духе. Внутри нет
флага «я не знаю». Именно поэтому в харнессе инструменты (прочитать реальный файл, запустить
команду) дают больше, чем любые просьбы «будь точным»: они подменяют догадку фактом.

## 5. Как модель реально работает во время генерации

### 5.1 Две разные фазы: prefill и decode

| | Prefill | Decode |
|---|---|---|
| Что делает | обрабатывает весь входной текст сразу | порождает по одному токену |
| Параллелится | да, по всем токенам входа | нет, каждый токен зависит от предыдущего |
| Чем ограничена | вычислениями (FLOPs) | скоростью чтения памяти |
| Что определяет | время до первого токена (TTFT) | скорость генерации (токенов/с) |

Первый токен ждать долго: модель обязана прогнать через все слои весь промпт. Дальше каждый
следующий токен — это один проход по всем весам, и он принципиально последовательный. Нельзя
«сгенерировать 100 токенов параллельно», потому что каждый следующий зависит от всех предыдущих.

### 5.2 KV-кэш: зачем он нужен и сколько ест памяти

Если бы модель на каждом шаге пересчитывала Key и Value для всех предыдущих токенов, генерация была
бы квадратично медленной. Поэтому их сохраняют — это и есть **KV-кэш**.

Формула размера:

```
байт на токен = 2 (K и V) × слоёв × kv-голов × размер головы × байт на число
```

Реальные числа (fp16, то есть 2 байта на число):

| Модель | Слоёв | KV-голов | KV на токен | 8k контекста | 128k контекста |
|---|---|---|---|---|---|
| 8B класса (GQA) | 32 | 8 | ~128 КБ | ~1.0 ГБ | ~16 ГБ |
| 70B класса (GQA) | 80 | 8 | ~320 КБ | ~2.6 ГБ | ~40 ГБ |
| 70B без GQA (64 головы) | 80 | 64 | ~2.5 МБ | ~20 ГБ | ~320 ГБ |

Последняя строка — ответ на вопрос «почему придумали GQA». GQA (grouped-query attention) — это
когда несколько голов внимания делят одну пару K/V. Качество почти не страдает, а память под кэш
падает в 8 раз. Без этого длинный контекст был бы физически невозможен.

Обрати внимание: KV-кэш **не входит в размер модели** и растёт с каждым пользователем. В
многопользовательском сервере он часто съедает памяти больше, чем сами веса. Отсюда трюки вроде
PagedAttention в vLLM: кэш хранят блоками, как страницы памяти в ОС, чтобы не тратить память на
фрагментацию.

### 5.3 Контекстное окно

Контекст — это всё, что модель видит в одном запросе: системный промпт, определения инструментов,
вся переписка, все выводы команд и файлов, плюс её собственный ответ. Не «память», а именно
одноразовый вход. Из этого следует:

- **API модели не имеет состояния.** Каждый запрос харнесс отправляет историю целиком заново. Именно
  поэтому длинный диалог дорожает и упирается в лимит.
- **Окно — жёсткая граница.** Переполнилось — харнесс обязан что-то выбросить или сжать (см. раздел
  про компакцию).
- **«Начало и конец видны, середина теряется».** Модели заметно хуже используют информацию из
  середины длинного промпта. Поэтому харнесс кладёт инструкции в начало, а свежие данные — в конец.
- **Заявленное окно ≠ рабочее качество.** Модель с окном 1M токенов на середине этого окна
  справляется хуже, чем на первых 20k. Окно — это техническая возможность, а не гарантия.

### 5.4 Батчинг: почему сервер обслуживает сотни пользователей одновременно

Ключевой факт: при генерации одного токена модель читает из памяти **все веса**, независимо от того,
одному пользователю она отвечает или ста. Значит, можно скормить ей сразу 32 запроса и прочитать
веса один раз на всех. Это **батчинг**: латентность почти та же, суммарная пропускная способность
почти в 32 раза выше. Современные серверы делают **continuous batching** — добавляют и убирают
запросы из батча на каждом шаге, не дожидаясь, пока все закончат.

Практическое следствие для тебя как пользователя: API-провайдер обычно ограничен вычислениями
(много батчей), а домашняя видеокарта — памятью. Поэтому API дёшев на поток и дорог на длинный
контекст, а локальный запуск — наоборот.

### 5.5 Откуда берётся конкретный токен (сэмплирование)

1. Модель выдаёт logits — по одному числу на каждый токен словаря.
2. Применяются штрафы (за повторы).
3. Делится на temperature.
4. Отсекаются маловероятные варианты (top_k, top_p, min_p).
5. Из оставшегося распределения выбирается токен (случайно или всегда самый вероятный).
6. Токен дописывается к тексту и всё повторяется.

Ещё один приём — **prompt caching**: провайдер запоминает вычисленное состояние для неизменного
префикса промпта и не пересчитывает его. Именно поэтому в агентских циклах, где 95% промпта не
меняется, кэшированный вход стоит в разы дешевле обычного. Роль харнесса здесь — следить, чтобы
префикс не менялся зря (например, не вставлять текущее время в начало промпта).

## 6. Параметры модели (не путать с параметрами генерации)

Это характеристики самой модели, зашитые при обучении. Их нельзя «покрутить» в запросе.

| Параметр | Что значит простыми словами | На что влияет |
|---|---|---|
| Число параметров (8B, 70B, 671B) | сколько чисел в весах | размер файла, требования к памяти, общая «мощность» |
| Число слоёв | глубина стопки блоков | способность к абстракции, память о далёком контексте |
| Скрытый размер (hidden size) | длина вектора на токен | ширина представлений, объём вычислений |
| Число голов / KV-голов | сколько независимых «взглядов» на контекст | качество связей и размер KV-кэша |
| Размер словаря | сколько токенов знает | длина текста в токенах, цена кириллицы |
| Контекстное окно | сколько токенов влезает в один запрос | сколько кода/файлов можно дать за раз |
| MoE или dense | все ли параметры работают на каждом токене | баланс «много знаний / мало вычислений» |
| Квантизация | точность хранения чисел | размер, скорость, лёгкая потеря качества |
| Дата среза знаний | до какого момента в обучении были данные | актуальность фактов |

### 6.1 MoE (mixture of experts) на пальцах

В обычной (dense) модели на каждом токене работают все веса. В MoE модель состоит из множества
«экспертов» (отдельных MLP-блоков), и на каждый токен маршрутизатор выбирает двух-четырёх из них.
Итог: модель хранит знания как большая (то есть файл огромный, память нужна под все веса), но
считает как маленькая (быстро).

Примеры: Mixtral 8x7B — 46.7 млрд параметров всего, ~12.9 млрд активных на токен. DeepSeek-V3 —
671 млрд всего, ~37 млрд активных. То есть для скорости ориентируйся на активные, для памяти — на
полные.

### 6.2 Квантизация

Числа в весах можно хранить с разной точностью:

| Формат | Байт на параметр | 7B | 70B | Что теряется |
|---|---|---|---|---|
| fp32 | 4 | 28 ГБ | 280 ГБ | ничего (эталон обучения) |
| bf16 / fp16 | 2 | 14 ГБ | 140 ГБ | почти ничего |
| fp8 / int8 | 1 | 7 ГБ | 70 ГБ | мало, часто незаметно |
| int4 (Q4, NF4) | ~0.5–0.6 | 3.5–4.5 ГБ | 35–45 ГБ | заметно на моделях до ~7B, слабо на крупных |

Практика: 4-битная квантизация большой модели обычно лучше, чем 16-битная маленькая, если вопрос
«качество на гигабайт памяти». Для 7B и меньше квантизация в 4 бита уже ощутимо портит код и
арифметику. Для 70B+ это почти бесплатно.

### 6.3 Открытые и закрытые веса

Открытые (Llama, Qwen, DeepSeek, Mistral, Gemma) можно скачать и запустить у себя — отсюда Ollama,
llama.cpp, vLLM, MLX. Закрытые (GPT, Claude, Gemini) доступны только через API. Разница не в
качестве как таковом, а в том, контролируешь ли ты железо, данные и версию модели.

## 7. Параметры генерации: что означают и что с ними делать

Это то, что харнесс передаёт вместе с запросом. Меняют не знания модели, а то, **как она выбирает
из своих же вероятностей**.

| Параметр | Простыми словами | Типичный диапазон |
|---|---|---|
| `temperature` | насколько смело выбирать не самый вероятный токен; 0 = всегда самый вероятный | 0…1 (выше 1 — уже рискованно) |
| `top_p` (nucleus) | оставить только варианты, суммарная вероятность которых ≥ p, остальное выкинуть | 0.9–1.0 |
| `top_k` | оставить ровно k самых вероятных вариантов | 20–100, часто выключен |
| `min_p` | выкинуть всё, что вероятнее самого вероятного менее чем в N раз | 0.02–0.1 |
| `repetition_penalty` | штраф за токены, которые уже были | 1.0–1.2 |
| `frequency_penalty` / `presence_penalty` | штраф за частые / за уже использованные токены (OpenAI-стиль) | −2…2, обычно 0 |
| `seed` | фиксирует случайность для воспроизводимости | любое число |
| `max_tokens` | жёсткий потолок длины ответа | по задаче |
| `stop` | строки, при которых генерация обрывается | — |
| `logit_bias` | вручную повысить/понизить вероятность конкретного токена | редко нужно |
| `logprobs` | вернуть вероятности выбранных токенов — для оценки уверенности | для отладки |
| `reasoning_effort` / бюджет «размышлений» | сколько токенов модель тратит на внутренние рассуждения | low/medium/high |
| `tools` + `tool_choice` | какие инструменты доступны и обязан ли модель их вызвать | см. раздел 9 |
| `response_format` | требовать JSON по схеме (constrained decoding) | для извлечения данных |

### 7.1 Что происходит внутри с temperature

Математически: `softmax(logits / T)`. При `T = 1` распределение как есть, при `T → 0` оно
превращается в «выбрать максимум» (жадный режим), при `T > 1` — выравнивается, и хвост словаря
получает шанс. Отсюда и «креативность»: модель начинает выбирать не самые очевидные слова —
и вместе с ними не самые очевидные ошибки.

`top_p` работает иначе: сортирует варианты по вероятности, набирает их сверху вниз, пока сумма не
достигнет `p`, и обрезает остальное. При `top_p = 0.9` модель в принципе не может выбрать токен из
дальних 10% вероятностной массы.

### 7.2 Практические настройки

| Задача | temperature | top_p | Комментарий |
|---|---|---|---|
| Код, вызовы инструментов, агент | 0–0.3 | 0.9–1.0 | нужна предсказуемость |
| Извлечение фактов, классификация, JSON | 0 | 1.0 | нужен один правильный ответ |
| Обычный диалог, объяснение | 0.5–0.7 | 0.95 | баланс |
| Тексты, brainstorm, нейминг | 0.8–1.0 | 0.95–1.0 | разнообразие важнее точности |
| Reasoning-модели | не трогать | не трогать | обычно параметры игнорируются, «усилие» задаётся отдельно |

Правила, которые экономят время:

- **Крутить что-то одно.** Одновременные `temperature` и `top_p` создают эффект, который трудно
  предсказать. Начни с `temperature`, оставив `top_p = 1.0`.
- **`temperature = 0` не значит «полный детерминизм».** На сервере запросы идут батчами, порядок
  сложений в плавающей точке меняется — ответы могут слегка отличаться. Для воспроизводимости нужны
  ещё `seed` и один и тот же бэкенд.
- **Не лечи температуру вместо промпта.** Если ответ неверный, а не «скучный», понижение
  температуры не поможет — поможет контекст и инструменты.

### 7.3 Про деньги

Вход и выход стоят по-разному, обычно выход дороже в 3–4 раза. Причина прямо в разделе 5: вход
обрабатывается пачкой и параллельно (prefill), а выход генерируется строго по одному токену, каждый
раз читая все веса из памяти (decode). Кэшированный вход стоит ещё в разы дешевле. Отсюда
агентские закономерности: длинная история переписки дорога, длинные рассуждения дороги, а вот
большой файл, прочитанный один раз, относительно дёшев.

## 8. Железо: почему всё решает память

### 8.1 Две скорости у любого ускорителя

У GPU есть две характеристики, и путать их — главная ошибка в рассуждениях про производительность:

1. **Сколько считает** — FLOPs (триллионы операций в секунду).
2. **Как быстро читает память** — пропускная способность, ГБ/с.

Отношение «операций на байт» называется арифметической интенсивностью. Если задача читает много, а
считает мало — упор в память (memory-bound). Если наоборот — упор в вычисления (compute-bound).

- **Decode** — память. На каждый токен надо прочитать все веса, а арифметики при этом мало.
- **Prefill и обучение** — вычисления. Там одни и те же веса применяются к тысячам токенов сразу.

Пропускная способность памяти, для ориентира:

| Железо | Память | ГБ/с |
|---|---|---|
| Обычный серверный CPU | DDR5, 8 каналов | ~300–500 |
| Ноутбук, LPDDR5 | 2 канала | ~80–120 |
| Apple M3 Max | унифицированная | ~400 |
| Apple M2/M3 Ultra | унифицированная | ~800 |
| RTX 4090 | GDDR6X 24 ГБ | ~1000 |
| A100 80 ГБ | HBM2e | ~2000 |
| H100 SXM | HBM3 | ~3350 |
| B200 | HBM3e | ~8000 |

Разброс в 40 раз между ноутбуком и H100 — вот почему одна и та же модель на одном железе отвечает
мгновенно, а на другом «печатает по букве в секунду».

### 8.2 Сколько нужно видеопамяти

Память под модель складывается из четырёх частей:

```
веса  +  KV-кэш  +  рабочие буферы (активации)  +  запас на фрагментацию
```

Пример: 70B в int4.
- веса ≈ 35–40 ГБ;
- KV-кэш ≈ 320 КБ на токен, на 8k контекста ≈ 2.6 ГБ на одного пользователя;
- буферы: 1–3 ГБ;
- итог: около 45 ГБ → в 24 ГБ одной потребительской карты не влезает, нужны 2 карты или
  Mac с 64+ ГБ.

Тренировка — совсем другая история. Кроме весов нужны градиенты и состояния оптимизатора Adam: это
ещё примерно 12–16 байт на параметр. Для 70B получается больше терабайта только на это. Поэтому
обучение и инференс — задачи с разницей в требованиях на порядок.

### 8.3 Прикидка скорости генерации

Для одного потока (один пользователь, один ответ) потолок считается так:

```
токенов/с ≈ пропускная способность памяти / объём данных, читаемых на токен
```

| Сценарий | Читаем на токен | Железо | Потолок | Реально |
|---|---|---|---|---|
| 8B int4 | ~4 ГБ | M3 Max, 400 ГБ/с | ~100 | 40–70 |
| 8B fp16 | ~16 ГБ | RTX 4090, 1000 ГБ/с | ~60 | 35–50 |
| 70B int4 | ~35 ГБ | M3 Max, 400 ГБ/с | ~11 | 5–8 |
| 70B fp16 | ~140 ГБ / 2 карты | 2×H100, 3350 ГБ/с каждая | ~45 | 20–40 |
| 671B MoE fp8 | ~671 ГБ / 8 карт | 8×H100 | ограничено активными 37B | десятки |

Реальные числа всегда ниже потолка в 2–3 раза: мешают накладные расходы, внимание, роутинг,
обмен между картами и температура чипов.

Отсюда простые выводы:

- **Хочешь быстрее на своём железе** — уменьшай то, что читается: квантизация, меньшая модель,
  меньший контекст. Больше ядер не поможет, если упор в память.
- **Хочешь обслужить больше людей** — батчинг. Он превращает задачу из memory-bound в
  compute-bound, и на этом выигрывают в разы.
- **Длинный контекст дорог дважды**: больше KV-кэша (память) и квадратичный рост внимания в
  prefill (время до первого токена).
- **Несколько карт соединяют NVLink/InfiniBand.** Через PCIe обмен медленный, и tensor parallelism
  (когда каждая карта считает свою часть каждого слоя) начинает тормозить.

### 8.4 Ускорения, о которых стоит знать по названиям

FlashAttention — переписанное внимание, экономящее память и обращения к ней. PagedAttention (vLLM) —
KV-кэш блоками, чтобы память не фрагментировалась. Speculative decoding — маленькая модель
предлагает несколько токенов вперёд, большая их проверяет одним проходом. llama.cpp / GGUF — запуск
квантованных моделей на CPU и Apple Silicon. MLX — то же самое родное для Mac.

## 9. Что такое харнесс

### 9.1 Определение

**Харнесс (harness) — это программа, которая превращает языковую модель в работающего агента.** Она
владеет циклом, состоянием и инструментами. Модель внутри этого цикла — сменный компонент.

Аналогия, которая точно отражает суть: LLM — это мозг в банке, который умеет только говорить; у
него нет ни рук, ни глаз, ни памяти, и каждые несколько секунд его память полностью стирается.
Харнесс — это тело, руки, блокнот, регламент безопасности и секретарь, который записывает всё
сказанное и подкладывает нужные бумаги к каждому следующему «пробуждению».

Ключевое: харнесс — **обычная программа**. В нём нет ничего магического, и его качество напрямую
видно в результате. Одна и та же модель в хорошем и плохом харнессе показывает разницу, сравнимую
с разницей между моделями разных поколений.

Харнесс **не** обучает модель, не хранит знания и не «думает». Он: собирает вход, зовёт модель,
исполняет просьбы, следит за лимитами, ведёт журнал.

### 9.2 Из чего он состоит

Ниже — список по функциям, с примерами из DSH (это реально установленные плагины; всё вместе —
пакеты `@deepseek-ai/dsh-*`).

**1) Транспорт до модели.** HTTP-клиент к провайдеру, стриминг ответа, повтор при ошибке 429/500,
таймауты, счёт токенов. В DSH это слои подключения к API плюс `dsh-token-meter`.

**2) Сборка промпта (контекста).** Самая недооценённая часть. Харнесс решает, что именно увидит
модель: системная инструкция, правила проекта (`AGENTS.md` → `dsh-agent-instructions`), текущее
время (`dsh-time-context`), описания инструментов, история диалога, свежие результаты команд. Это
и есть «программирование модели»: отдельного канала управления, кроме текста, не существует.

**3) Реестр инструментов.** Каждый инструмент — это имя, текстовое описание и JSON-схема
аргументов. Модель видит этот список и может «попросить» вызвать инструмент. В DSH инструменты —
это плагины: `dsh-tool-fs` (чтение/запись/правка файлов), `dsh-tool-fs-search` (поиск), `dsh-tool-bash`
(команды), `dsh-tool-web` (поиск и загрузка страниц), `dsh-tool-todo`, `dsh-tool-jobs`,
`dsh-tool-skill`, `dsh-tool-ask-user`, `dsh-tool-goal`, `dsh-tool-subagent`, `dsh-tool-workflow`,
`dsh-tool-ralph`. Отдельная деталь: в DSH нет инструмента `cat` для чтения файлов — чтение идёт
через `read`, потому что тогда харнесс видит факт чтения и может применить политики (см. пункт 5).

**4) Цикл агента.** Сердце харнесса: «отправить контекст → получить ответ → если в ответе есть
запросы инструментов, выполнить их → добавить результаты в контекст → повторить». Условие выхода:
модель ответила текстом без вызовов, или сработал лимит шагов, или пользователь прервал.

**5) Политики и безопасность.** Правила, которые харнесс навязывает независимо от желаний модели:
песочница для команд (`dsh-fs-sandbox`, `dsh-bash-sandbox`, `dsh-sandbox-policy`), обязательное
чтение файла перед правкой (`dsh-fs-observation-policy`), подтверждение опасных действий
(в этой сессии, например, подтверждения отключены — и это тоже политика харнесса, а не свойство
модели). Когда инструмент отклонён песочницей, модель видит текст вида
`[sandbox: file access denied]` — то есть границу рисует харнесс, а модель лишь читает сообщение.

**6) Управление контекстом.** Токены считаются, длинные выводы обрезаются (в DSH, например,
показывается хвост, а полный вывод сохраняется в файл и путь сообщается), старые результаты
инструментов вычищаются (`dsh-compaction-tool-result-pruner`), при переполнении окна история
сжимается в пересказ (`dsh-compaction-basic`, команда `/compact`). Это не «оптимизация», а
необходимое условие работы: без компакции агент умирает на длинной задаче.

**7) Состояние и журнал.** Сессии сохраняются, их можно возобновить, отфоркать, экспортировать
(`dsh-session-persistence`, `dsh-session-query`, `dsh-session-log-export`, `dsh-session-projection`).
История — не «память модели», а файл, который харнесс снова подкладывает модели.

**8) Оркестрация.** Субагенты, воркфлоу, фоновые задачи, цели, расписания
(`dsh-tool-subagent`, `dsh-tool-subagent-control`, `dsh-tool-workflow`, `dsh-goal`,
`dsh-schedule`). Всё это тоже харнесс: модель лишь просит «запусти отдельного агента с таким
промптом», а процессы, передача результатов и лимиты — на стороне харнесса.

**9) Внешние интеграции.** MCP-клиент (`dsh-mcp-client`) — стандарт, через который к харнессу
подключают чужие инструменты (Jira, Slack, базы, браузер). Скиллы (`dsh-skill`,
`dsh-skill-filesystem`) — папки с инструкциями, которые подгружаются по требованию. Хуки
(`dsh-hooks-claude-code`, `dsh-hooks-codex`) — совместимость с хуками чужих харнессов.
Вебхуки (`dsh-webhook-github`) — реакция на события извне.

**10) Интерфейсы.** Один и тот же движок с разными «мордами»: веб-UI (`dsh-web-app` — то, что
открыто у тебя на `127.0.0.1:3080`), терминал, headless-запуск одной задачи, SDK по JSON-RPC, ACP
для сторонних редакторов. Модель об этом не знает вообще.

### 9.3 Что делает модель, а что харнесс

| Шаг | Модель | Харнесс |
|---|---|---|
| Решить, что делать дальше | да | — |
| Сформулировать аргументы вызова инструмента | да | — |
| Проверить, что аргументы валидны по схеме | — | да |
| Выполнить команду или правку файла | — | да |
| Ограничить доступ (песочница, подтверждения) | — | да |
| Записать результат в контекст | — | да |
| Следить за лимитом токенов и сжимать историю | — | да |
| Помнить, что было 50 шагов назад | только через текст, который дал харнесс | да |
| Остановиться | может сказать «готово» | решает по лимитам и условиям |

## 10. Как харнесс и LLM взаимодействуют: один шаг целиком

### 10.1 Протокол

Разговор идёт по HTTP в формате JSON. В запросе — список сообщений с ролями и описания
инструментов:

```json
{
  "model": "some-model",
  "messages": [
    {"role": "system", "content": "Ты агент. Правила: ..."},
    {"role": "user", "content": "почини падающий тест"},
    {"role": "assistant", "content": "Сначала посмотрю файл.",
     "tool_calls": [{"id": "c1", "name": "read", "arguments": {"file_path": "src/a.ts"}}]},
    {"role": "tool", "tool_call_id": "c1", "content": "1  export function f() {...}"}
  ],
  "tools": [
    {"name": "read", "description": "Читает файл",
     "parameters": {"type": "object", "properties": {"file_path": {"type": "string"}},
                    "required": ["file_path"]}}
  ],
  "temperature": 0.2
}
```

Ответ модели — либо обычный текст, либо `tool_calls` (тот же JSON, только порождённый моделью),
либо и то и другое.

### 10.2 Что здесь важно понять

- **Модель ничего не исполняет.** `tool_calls` — это текст, который харнесс распарсил. Модель
  «попросила», харнесс «сделал». Если бы харнесс проигнорировал запрос, ничего бы не произошло.
- **Результат инструмента — просто текст в следующем сообщении.** Модель не «видит» файловую
  систему, она видит строку, которую харнесс ей подсунул. Поэтому обрезанный вывод команды для неё
  абсолютная истина.
- **API без состояния.** Вся история отправляется заново на каждом шаге. Отсюда прямая связь:
  длина истории → цена → необходимость компакции.
- **Ошибка — тоже результат.** Ненулевой код возврата, отказ песочницы, невалидный JSON — всё это
  возвращается модели текстом, и она на это реагирует. Поэтому в DSH к каждому выводу команды
  приписывается `[exit code: N]`, а команда «не забудь проверить код возврата» стоит в инструкции:
  без этого модель считает любой вывод успехом.
- **Схема инструмента — это подсказка.** Описание и параметры определяют, как модель будет
  инструментом пользоваться. Инструмент с плохим описанием работает плохо у любой модели.

### 10.3 Разбор реального шага

Задача: «почини падающий тест».

1. Харнесс собирает промпт: системная инструкция + правила проекта из `AGENTS.md` + сегодняшняя
   дата + список инструментов + твоя фраза. Считает токены.
2. Отправляет модели. Та отвечает текстом «посмотрю тест» и запросом `read` на файл.
3. Харнесс валидирует аргументы, читает файл с диска, обрезает до лимита, помечает, что файл
   прочитан (это разрешит последующую правку — политика «нельзя править то, что не читал»), и
   добавляет результат в контекст.
4. Модель отвечает запросом `grep` по проекту. Харнесс запускает поиск, возвращает совпадения.
5. Модель отвечает запросом `edit` с новым фрагментом. Харнесс проверяет, что старый фрагмент
   существует ровно в одном месте, применяет правку.
6. Модель отвечает запросом `bash` — запустить сборку. Харнесс выполняет команду в песочнице,
   возвращает вывод и код возврата.
7. Если код не ноль — модель читает вывод и делает следующий шаг. Если ноль — пишет текстовый
   ответ без вызовов инструментов, и цикл заканчивается.
8. По ходу харнесс считает токены; если контекст подходит к границе — вычищает старые результаты
   инструментов или сжимает историю, чтобы цикл не оборвался.

Всё, что здесь «умное», распределено: решения — у модели, исполнение и дисциплина — у харнесса.

### 10.4 Как инструменты меняют поведение модели

Один и тот же LLM без инструментов и с инструментами — две разные системы:

- С инструментом чтения файла — отвечает по реальному коду. Без него — по памяти о похожем коде,
  то есть выдумывает.
- С возможностью запустить команду — узнаёт правду о сборке. Без неё — предполагает.
- С поиском в вебе — знает актуальное. Без — опирается на дату среза знаний.
- С субагентами — может разгрести большую задачу, не забивая свой контекст.
- С политикой «прочитай перед правкой» — не переписывает файл наугад.

Это и есть причина, по которой «харнесс» — не обвязка, а половина результата.

## 11. Как всё это связано: сквозная картина

```
ты (задача)
   │
   ▼
[ харнесс ]  ── собирает контекст ──►  [ LLM на сервере/локально ]
   ▲                                        │
   │                                        ▼
   │                              вероятности следующего токена
   │                                        │
   │                              сэмплирование → токен
   │                                        │
   └──── исполняет tool_calls ◄──── текст или запрос инструмента
         (файлы, команды, сеть)
```

- Харнесс живёт на твоём компьютере и стоит копейки.
- Модель живёт на GPU, где всё решает память: сколько весов прочитано на токен и сколько
  KV-кэша занято.
- Контекст — единственный канал управления: то, что харнесс положил в промпт, и есть «мозг» и
  «память» агента на этот шаг.
- Инструменты — единственный способ взаимодействия с миром, и выполняет их всегда харнесс.

## 12. Частые заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Модель помнит наш прошлый чат» | Не помнит. Харнесс переслал ей историю заново |
| «Модель сама лезет в интернет» | Нет. Харнесс вызывает поиск и подкладывает текст модели |
| «Больше параметров — всегда лучше» | Хорошо обученная и хорошо квантованная модель поменьше часто побеждает старую большую |
| «Окно 1M значит, что модель использует 1M» | Технически влезает; качество на середине длинного контекста заметно ниже |
| «Temperature = интеллект» | Temperature = разброс выбора. Для кода и фактов он только вредит |
| «Temperature 0 — полный детерминизм» | Батчинг и плавающая точка дают небольшие расхождения |
| «4-битная квантизация ломает модель» | Для крупных моделей потери малы, для 7B и меньше — ощутимы |
| «Модель запускается на моём ноутбуке» | Обычно на чужой GPU; локально запускают только открытые модели |
| «Агент сам решает, что ему доступно» | Доступ определяет харнесс: песочница, подтверждения, набор инструментов |
| «Промпт-инжиниринг важнее инструментов» | Инструменты дают больше: факт из файла сильнее любой формулировки |

## 13. Практика: что реально влияет на результат

По убыванию отдачи:

1. **Есть ли у агента нужные инструменты** (доступ к файлам, командам, поиску, базам).
2. **Качество контекста**: правильные файлы, свежие данные, точные инструкции в `AGENTS.md`.
3. **Выбор модели** под задачу: для правок в коде и длинных цепочек нужна сильная модель, для
   переименований и рутины хватает маленькой и дешёвой.
4. **Управление контекстом**: компакция, обрезка выводов, разбиение задачи.
5. **Параметры генерации**: обычно низкая temperature и ничего больше.
6. **Формулировка задачи**: важна, но это влияние слабее, чем пункты 1–3.

Практические ориентиры по выбору:

| Ситуация | Что разумно |
|---|---|
| Правки в большом репозитории, длинные цепочки шагов | сильная модель через API, хороший харнесс, компакция включена |
| Много однотипной рутины | маленькая модель, автоматизация, минимум инструментов |
| Данные не должны уходить наружу | открытая модель локально, но потери в скорости и качестве |
| Нужен точный JSON | `temperature = 0` + схема ответа (constrained decoding) |
| Нужно дешево | короткий контекст, кэш промпта, поменьше итераций |

Локальный запуск: `llama.cpp` или Ollama для GGUF-моделей, MLX для Apple Silicon, vLLM для сервера
с батчингом. Разумный компромисс для домашнего железа — 7B–32B в 4-битной квантизации.

## 14. Глоссарий

| Термин | Значение |
|---|---|
| Токен | Кусочек текста из словаря модели; единица измерения контекста и цены |
| Токенизатор | Программа, режущая текст на токены (BPE) |
| Веса / параметры | Числа модели; то, что занимает место на диске и в видеопамяти |
| Logits | Баллы модели по каждому токену словаря до превращения в вероятности |
| Softmax | Превращение баллов в вероятности |
| Attention | Механизм, дающий токенам смотреть друг на друга |
| Q / K / V | Три вектора на токен во внимании: что ищу, что предлагаю, что отдаю |
| Голова (head) | Один независимый канал внимания |
| GQA | Несколько голов внимания делят пару Key/Value; экономит KV-кэш в разы |
| MLP / FFN | Слой «памяти фактов» внутри блока трансформера |
| Остаточная связь | Прибавление входа слоя к выходу; без неё глубокая сеть не обучается |
| RoPE | Кодирование позиции через вращение векторов |
| Prefill | Обработка всего входного текста сразу; определяет задержку до первого токена |
| Decode | Генерация по одному токену; упирается в пропускную способность памяти |
| KV-кэш | Сохранённые Key и Value предыдущих токенов, чтобы не считать их заново |
| Контекстное окно | Максимум токенов в одном запросе |
| Prompt caching | Кэширование неизменного префикса промпта на стороне провайдера |
| Батчинг | Обработка нескольких запросов за один проход; растёт пропускная способность |
| MoE | Модель из экспертов; активных параметров меньше, чем всего |
| Квантизация | Хранение весов в меньшей точности (fp8, int8, int4) |
| Температура | Масштаб случайности при выборе токена |
| Top-p / Top-k / Min-p | Способы отсечь маловероятные варианты перед выбором |
| Reasoning-модель | Модель, обученная тратить токены на внутренние рассуждения перед ответом |
| Greedy decoding | Всегда брать самый вероятный токен (temperature → 0) |
| Галлюцинация | Правдоподобный, но неверный текст; следствие природы модели |
| Харнесс | Программа, которая ведёт цикл агента, держит инструменты и контекст |
| Инструмент (tool) | Функция, которую может «попросить» модель; выполняет её харнесс |
| Tool call | Запрос модели на вызов инструмента в структурированном виде |
| Агентский цикл | Многократное «модель → инструмент → результат → модель» |
| Компакция | Сжатие истории диалога, когда контекст переполняется |
| MCP | Стандарт подключения внешних инструментов к харнессу |
| Скилл | Папка с инструкциями, подгружаемыми по требованию |
| Субагент | Отдельный экземпляр агента со своим контекстом, запущенный харнессом |
| TTFT | Time to first token: сколько ждать первого токена |
| FLOPs | Операции в секунду: «вычислительная» скорость железа |
| Пропускная способность | ГБ/с чтения памяти; главный ограничитель генерации |
| Memory-bound / compute-bound | Задача упирается в память / в вычисления |
