# План: режим «Улучшить» в разделе Медиа — поиск дублей и слабых снимков

Задача: в разделе «Медиа» появляется отдельный режим (переключатель рядом с названием
раздела, как в Google Photos «Похожие фото»). Он находит дубли, почти-дубли и «слабые»
снимки (мыло, промах, закрытые/отсутствующие глаза), показывает их в виде групп, где
отмечен лучший снимок, и предлагает удалить лишние **в корзину** (не сразу, через
подтверждение). Автоудаления нет и не будет: сервер только предлагает, человек решает.

Работает только с фото (видео в поиск дублей не включаем — кадр из видео и фото рядом
с ним — ложный дубль; видео как «слабое» — отдельная история, здесь нет).

## 1. Где и как считается

Сервером, фоновым индексатором. Причин три:

1. **Превью уже лежат в S3.** Для каждого фото зоны «Фото» с `previewState = 'done'`
   собраны два AVIF: квадрат 256×256 (`view/<sha>-grid.avif`) и полный 1080×1080
   (`view/<sha>-1080.avif`). Индексатор читает готовые превью (`S3Service.getObjectBytes`)
   и не трогает оригиналы ни байтом. Оригинал нужен только в одном месте — при выборе
   лучшего в группе (см. п. 5), и только у двух-трёх кадров.
2. **CPU-алгоритмы.** pHash — это ДКБ 32×32 через sharp (libvips), микросекунды на кадр.
   Сравнивание хэшей — побитовая XOR. Face detection — MediaPipe Tasks face detector
   (BlazeFace, tflite) — десятки миллисекунд на 1080-превью на CPU. GPU не требуется.
3. **Одно место.** Телефон может быть отключён, веб-браузер — открыт, но и то и другое
   видит один результат, потому что группы считаются один раз на сервере и кладутся в
   базу.

Индексатор — отдельный NestJS-сервис со своим циклом (не очередь конвертации: у неё
другой ритм — задачи ставит клиент, а здесь работа плановая и массовая).

## 2. Алгоритм поиска

Три вида групп:

### 2.1 Точные дубли — `sha256`

Уже есть в базе (Asset дедуплицирован по хэшу). Отдельная группа для каждого sha, у
которого **несколько живых** FileEntry в зоне «Фото». Хэш считать не нужно — только
счётчик. Такие группы самые дешёвые и самые безопасные.

### 2.2 Почти-дубли — временной кластер, затем pHash

Поиск почти-дублей идёт в два слоя. Таймштамп — **не критерий** дубля (бурст из 10
разных кадров в одну секунду — это 10 разных фото), а **предфильтр кандидатов**:
большинство дублей сделано в один момент времени (сериальная съёмка, повторный запуск,
две копии одного снимка), поэтому сравнивать хэши нужно только внутри узкого
временного окна.

**Слой 0 — временные кластеры (дёшево, один проход).**
Кадры пользователя уже идут отсортированными по `capturedAt` (тот же порядок, что у
ленты «Медиа»). Проход со скользящим окном: кадр входит в тот же кластер, что и
предыдущий, если разница ≤ `T_CLUSTER` (дефолт **60 секунд**). Кадры без даты
(`capturedAt IS NULL`) в кластеры не попадают — для них near-поиск не работает,
и это нормально: точные дубли (sha256) их всё равно ловят.

Эффект: на практике 95% near-групп — бурсты, и каждая живёт внутри своего кластера
из нескольких-десятков кадров. Сравнивать нужно хэши внутри кластеров, а не по
всей библиотеке — это и есть главный источник ускорения.

**Слой 1 — pHash внутри кластеров.**
pHash (перцептивный хэш): ДКБ до 32×32, сравнение среднего, 64 бита. Устойчив к:
сжатию (JPEG/HEIC/AVIF на любом качестве), небольшому изменению размера, лёгкому
шуму. Чувствителен к: кадрированию, повороту, сильному ретушированию (и это правильно —
ретушь это уже другая фотография, а не дубль).

Порог: **hamming ≤ 10** для одной пары (калибруется на реальной библиотеке, см. п. 8).
Хэш храним в БД как `BIGINT`, расстояние — побитовый XOR и popcount (в памяти).

Внутри кластера пар мало (размер кластера обычно < 30), поэтому сравниваем все пары
кластера напрямую — O(k²) внутри кластера. Отдельные бит-слисинг-индексы по хэшу
не нужны: они решали задачу «сравнить все хэши библиотеки со всеми», которую
временной слой уже снял (см. п. 3 — колонок `h1..h4` в схеме нет).

Связность: кадры в near-группе объединяем Union-Find по найденным парам (a~b и b~c
дают группу a,b,c даже если a~c не прошло порог).

**Честные ограничения этого построения:**
- Дубль с разницей дат больше окна (ретушированная копия, сохранённая через неделю) —
  near-поиск не найдёт. Точные дубли (sha256) такие случаи ловят всегда.
- Кадрированные дубли (тот же кадр, обрезан по-разному) pHash не найдёт — ограничение
  алгоритма, не баг. Если захочется ловить и их — это эмбеддинги (п. 9), по умолчанию
  не включаем.
- UI-бонус: временной кластер сам объясняет группу — «сегодня, 14:32, 4 похожих фото» —
  пользователь видит серию с одного момента, а не абстрактную «группу похожих».

### 2.3 Слабые снимки — метрики качества

Для каждого фото зоны «Фото» с готовым превью считаем **один раз** набор метрик
(и хэш, и метрики — в одном проходе индексатора):

| Метрика | Считается из | Что значит |
|---|---|---|
| `sharpness` | 1080-превью, variance of Laplacian (sharp умеет) | Мыло/失фокус. Ниже порога — «мыльный» снимок |
| `exposureClip` | гистограмма 1080-превью (sharp `.stats()`) | Доля пикселей, упрятанных в 0/255. Много — пересвет/недосвет |
| `blurSize` | `MediaMeta.width/height` | Кадр меньше порога (например, 800×600) — скриншот/заставка, в «слабые» не попадает сам по себе, но участвует в ранжировании |
| `faceCount` | MediaPipe face detector на 1080-превью | 0 лиц там, где группа-дубль — с лицами: «с лица убрали» |
| `eyeOpen` | MediaPipe eye detector (отдельная модель, ~10 мс/лицо) | Все лица с закрытыми глазами — «моргнули» |

Метрики кладём в БД (одна строка на ассет, см. п. 3). «Слабая» группа — это не отдельный
поиск: это **фильтр по метрикам** поверх тех же кадров. Например:

- «Моргнувшие»: `faceCount > 0 AND eyeOpen = 0`;
- «Мыльные»: `sharpness < T_sharp` (T — медиана по библиотеке × 0.25, адаптивный порог);
- «Пересвеченные / недосвеченные»: `exposureClip > 0.15`.

Пороги — адаптивные (относительно медианы библиотеки), не жёсткие: у одного фотографа
«мыло» другое, чем у другого. Конкретные значения — в коде с комментариями, в документе
только принцип.

`T_CLUSTER` (окно временного кластера, п. 2.2) — не адаптивный, а фиксированный
параметр: 60 секунд. Адаптивничать здесь нечего — это «серия с одного момента»,
а физика серийная съёмки не зависит от фотографа.

## 3. Схема БД

Две новые модели в `prisma/schema.prisma`:

```prisma
// Хэш + метрики качества одного ассета (одна строка на sha256).
// Заполняется индексатором для фото зоны «Фото» с previewState='done'.
// Видео, PDF, BMP/JXL (impossible) — строк нет.
model MediaHash {
  id           String   @id @default(uuid())
  assetId      String   @unique
  asset        Asset    @relation(fields: [assetId], references: [id], onDelete: Cascade)

  // pHash: 64 бита в BIGINT. Postgres-овский BIGINT — signed, а хэш unsigned,
  // поэтому храним как BigInt в Prisma (он сам мапит в BIGINT), а расстояние
  // считаем в JS (BigInt XOR + countBits) — в SQL это короче не делается.
  phash        BigInt?

  // Метрики качества (п. 2.3).
  sharpness    Float?
  exposureClip Float?   // 0..1
  faceCount    Int?
  eyeOpen      Boolean? // true — хотя бы одно лицо с открытыми глазами

  // Когда считали (для повторного прогона «только новые»).
  computedAt   DateTime @default(now())
}

// Сгруппированные кадры, которые показываем в режиме «Улучшить».
// Группу строит индексатор, а не запрос на лету: поиск пар — дорогая операция,
// а группы нужны в UI стабильно (пользователь может вернуться через неделю).
model CleanupGroup {
  id           String   @id @default(uuid())
  userId       String
  user         User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  // exact_sha — точные дубли по sha256; near — почти-дубли по pHash; weak — слабые
  // снимки (мыло/моргание/экспозиция).
  kind         String   // 'exact_sha' | 'near' | 'weak'
  // Внутри near/weak — какой именно признак (для подписи в UI):
  //   near: 'phash'
  //   weak: 'blur' | 'blink' | 'exposure'
  reason       String?

  // Снимок состава группы на момент расчёта. Кадры в группе — FileEntry (не Asset):
  // один и тот же sha может лежать в двух папках, и это два разных кадра для UI.
  entryIds     String[] // id FileEntry, живых на момент расчёта

  // Лучший кадр в группе (см. п. 5). Для exact_sha — любой (всё одно и то же).
  bestEntryId  String?

  // Суммарный объём, который освободится, если удалить всё кроме лучшего.
  // Считаем один раз в БД, а не каждый раз в UI.
  savedBytes   BigInt   @default(0)

  // Состояние: active — показываем; resolved — пользователь разобрался (удалил или
  // проигнорировал); скрытые группы не удаляем, чтобы повторный прогон не показывал
  // то же самое.
  state        String   @default("active") // 'active' | 'resolved'

  createdAt    DateTime @default(now())
  resolvedAt   DateTime?

  @@index([userId, state])
}
```

Связь `User — CleanupGroup` по `userId` с каскадным удалением (группы — производные
данные, с пользователем уходят). `MediaHash` связан с `Asset` (не с `FileEntry`):
метрика качества — свойство содержимого, а не конкретной записи в дереве.

## 4. Индексатор

Отдельный сервис `src/media-cleanup/cleanup.service.ts` (модуль `MediaCleanupModule`),
свои зависимости: `PrismaService`, `S3Service`, `MediaService` (для `mediaKindOf`,
ключей превью), `AuthService` (для `subtreeIds`). Запускается на `onModuleInit` со
своим циклом и собственным «стоп-флагом» (аналог `QueueState.paused`, но отдельная
строка `CleanupState` в БД, чтобы пауза конвертации не влияла на индексацию и наоборот).

### 4.1 Что индексируем

Запрос по библиотеке пользователя (аналог `MediaFeedService.scope`, но с доп. условием):

```sql
FROM "MediaMeta" mm
JOIN "Asset" a ON a."id" = mm."assetId"
JOIN "FileEntry" f ON f."assetId" = a."id"
WHERE f."deletedAt" IS NULL
  AND f."zone" = 'PHOTOS'
  AND f."folderId" = ANY(:tree)
  AND a."previewState" = 'done'
  AND a."mime" LIKE 'image/%'          -- только фото, видео не индексировано
  AND mm."width" IS NOT NULL           -- есть размер (RAW без превью уже отфильтрован)
```

Строки, у которых уже есть `MediaHash` с `computedAt` свежее порога (например, 30 дней),
пропускаются. Новые кадры (появились с последнего прогона) — индексироваться.

### 4.2 Проход по одному фото

```
1. Получить 1080-превью: S3Service.getObjectBytes(view/<sha>-1080.avif)
   (квadrat 256×256 для pHash тоже годится, но 1080 нужен для метрик — читаем один объект).
2. pHash: sharp(buf).greyscale().resize(32,32).raw().toBuffer({resolveWithObject:true})
   → ДКБ, сравнение со средним, 64 бита. (sharp не считает pHash сам — 10 строк кода
   над raw-буфером, см. реализацию `imagehash`.)
3. Метрики:
   - sharpness: sharp(buf).greyscale().toBuffer() → variance of Laplacian
     (ручной проход по пикселям 3×3, либо sharp.convolve с ядром Лапласа и
     .stats().mean — второй вариант короче).
   - exposureClip: sharp(buf).stats() → доля пикселей с каналом 0 и 255.
   - faces: MediaPipe face detector (tflite, CPU) на том же буфере → число лиц;
     если лица есть — eye detector на каждом crop.
4. Записать MediaHash (upsert по assetId).
```

Темп: 1080-превью читается с S3 за ~100 мс (оно ~50-100 КБ), pHash + метрики — ~50 мс,
face detection — ~50-100 мс. Итого ~300 мс на кадр, или ~30 кадров/сек на одном потоке.
Библиотека в 100 000 кадров — ~1 час первого прогона. Это фоновая работа, не запрос
клиента, поэтому нормально. Повторные прогоны — только новые кадры (секунды).

**Память:** 1080-превью — ~1 МБ в буфере, MediaPipe модель — ~5 МБ в памяти. Ограничение
`WORKER_MEM_KB` из очереди не применяем (это отдельный процесс/поток), но держим в уме.

### 4.3 Группировка

После того как по библиотеке пользователя все `MediaHash` готовы, строим группы:

1. **exact_sha:** `SELECT sha256, array_agg(id) FROM FileEntry WHERE zone='PHOTOS' AND
   deletedAt IS NULL AND folderId = ANY(tree) GROUP BY sha256 HAVING count(*) > 1`.
   Каждая такая пара — группа `kind='exact_sha'`.
2. **near:** кадры пользователя (живые, фото, с `capturedAt`) разбиваем на временные
   кластеры окном `T_CLUSTER` (п. 2.2, слой 0); внутри каждого кластера — все пары
   pHash с порогом hamming ≤ 10; найденные пары объединяем Union-Find в связные
   компоненты и отбрасываем группы из 1 кадра.
   Кадр из exact_sha-группы не дублируется в near-группу (иначе один и тот же кадр
   попадёт в две группы и UI будет путать).
3. **weak:** фильтр по метрикам (п. 2.3). Кадр, уже в exact/near-группе, в weak не идёт
   (дубль — более важная причина удалить его, чем «мыло»).

Группы пишем в `CleanupGroup` (новые — создаём; старые `active` — перечитываем состав,
если в группе появился/исчез кадр). `savedBytes` — сумма размеров ассетов минус лучший.

### 4.4 Повторные прогоны

- **По расписанию:** раз в сутки (настраивается), прогон по новым кадрам.
- **По событию:** клиент после выгрузки нового фото может поставить `POST /media/cleanup/
  refresh` (soft-запрос: «есть время — посмотри»). Сервер ставит флаг, индексатор
  подхватывает в следующем цикле.
- **Ручной:** кнопка «Обновить» в режиме «Улучшить» — тот же soft-запрос.

## 5. Выбор лучшего в группе

Правило ранжирования (от худшего к лучшему), применяется к near-группам:

1. **Чёткость** (variance of Laplacian) — главный фактор. Мыло проигрывает чёткому всегда.
2. **Размер** (width × height) — при равной чёткости выигрывает больший.
3. **Лица/глаза** — при равных п.1-2: кадр с открытыми глазами выигрывает у моргнувшего.
4. **Экспозиция** — при равном выше: меньше обрезанная часть гистограммы — лучше.
5. **Дата** — при равном выше: новее (повторная съёмка обычно «исправляет» первую).

Для exact_sha-групп «лучший» — формальность (всё одно и то же), но выбираем самый свежий
FileEntry (по `updatedAt`), чтобы «оставить» тот, что в более важной папке, если владелец
руками передвигал.

**Оригинал для уточнения:** если два кадра в группе имеют одинаковую чёткость по
1080-превью (разница < 5%), читаем **оригинал** только этих двух-трёх кадров
(`S3Service.getObjectBytes(files/<sha>)`, с тем же лимитом `MAX_PARSE_BYTES`), считаем
чёткость на полном разрешении и решаем. Это единственное место, где индексатор трогает
оригинал, и только в спорных случаях.

## 6. API

Новый модуль `src/media-cleanup/` (controller + service), три ручки:

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/media/cleanup/groups` | Список активных групп пользователя: `[{id, kind, reason, entryIds, bestEntryId, savedBytes, count}]` + `totalSavedBytes`. Пагинация: по 50 групп. Миниатюры клиент тянет сам по `entryId` (уже умеет). |
| POST | `/media/cleanup/groups/:id/resolve` | `{action: 'deleted' \| 'ignored', deletedEntryIds: [...]}`. Отмечает группу `resolved`. `deleted` — клиент уже удалил записи через обычный `DELETE /files/:id` (в корзину); сервер только фиксирует, что группу разобрали. |
| POST | `/media/cleanup/refresh` | Soft-запрос «пересчитать новые кадры». Сервер ставит флаг, отвечает `{queued: true}`. |

Удаление самих кадров идёт **через существующую** `DELETE /files/:id` → `softDelete`
(в корзину). Никаких новых путей удаления: корзина, восстановление, retention — всё
уже работает. Режим «Улучшить» только предлагает, а действие — стандартное.

## 7. Клиент (Flutter)

### 7.1 Переключатель

В шапке `GalleryScreen` (рядом с названием «Медиа») — переключатель «Сетка / Улучшить».
Состояние — Riverpod `StateProvider<bool>` в `gallery_screen.dart`, не новый таб:
`IndexedStack` в `Shell` не трогаем (режим — внутри вкладки Медиа, как в Google Photos).

### 7.2 Экран режима «Улучшить»

- Список групп (каждая — карточка): превью лучшего кадра крупно, рядом миниатюры
  остальных в группе, подпись вида «3 похожих фото · освободит 12.4 МБ», бейдж причины
  («похожие», «мыльные», «моргнувшие»).
- Тап по группе → деталка: сетка кадров в группе, лучший помечен галочкой «оставить»,
  остальные — чекбоксы по умолчанию (отмечены к удалению), можно снять.
- Кнопка «Удалить в корзину (N)» → подтверждение → `DELETE /files/:id` на каждую
  отмеченную запись → `POST /media/cleanup/groups/:id/resolve` с `action: 'deleted'`.
- Кнопка «Пропустить» → `resolve` с `action: 'ignored'`.
- Сверху — сводка: «Найдено N групп, можно освободить X МБ».
- Кнопка «Обновить» → `POST /media/cleanup/refresh` + перезапрос списка групп.

### 7.3 Файлы

- `flutter/lib/features/gallery/cleanup_screen.dart` — новый экран режима.
- `flutter/lib/features/gallery/cleanup_provider.dart` — Riverpod: список групп,
  состояние деталки, действия (удалить/пропустить).
- `GalleryScreen` — переключатель в шапке, `AnimatedSwitcher` между сеткой и
  `CleanupScreen`.

## 8. Калибровка порогов

Первый прогон индексатора пишет в лог распределение: медиану/квартили `sharpness`,
`exposureClip`, число found near-групп при разных порогах (5, 8, 10, 12 по hamming).
На реальной библиотеке владельца подбираем:
- `H_AMMING_NEAR` — порог pHash (дефолт 10);
- `T_CLUSTER` — окно временного кластера (дефолт 60 с, п. 2.2); на большой библиотеке
  смотрим, не сливаются ли в один кластер две разные серии (если да — сужаем до 30 с);
- `T_SHARP` — доля медианы, ниже которой «мыло» (дефолт 0.25);
- `T_CLIP` — порог обрезанной экспозиции (дефолт 0.15).

Все четыре — константы в `cleanup.service.ts` с комментариями «подобрано на библиотеке
X кадров, дата», легко поменять и пересчитать.

## 9. Что НЕ делаем (и почему)

- **Автоудаление.** Нет. Сервер только предлагает, человек решает. Как в Google Photos.
- **Видео в поиск дублей.** Нет: кадр из видео и фото рядом — ложный дубль, а
  видео-дубли (та же запись, два файла) ловит уже exact_sha.
- **Эмбеддинги (сентенс-сходимость).** Не по умолчанию: они ловят «похожие сцены»
  (два разных кошелька на фоне), а не дубли. Это другая фича («похожие фото» в
  полном смысле), не «почистить». Если захочется — отдельный режим, отдельный индекс,
  CPU-инференс (MobileNetV3/small) на 1080-превью, ~50 мс/кадр, тоже без GPU.
- **Кадрированные дубли.** pHash их не найдёт (ограничение алгоритма). Эмбеддинги —
  да, но см. выше.
- **Повторное чтение оригиналов для метрик.** Нет: метрики — только с превью.
  Оригинал — только при спорном выборе лучшего (п. 5), и только у пары кадров.

## 10. Порядок работы

1. Миграция Prisma: `MediaHash`, `CleanupGroup`, `CleanupState`.
2. `src/media-cleanup/`: service (индексатор + группировка) + controller (3 ручки).
   MediaPipe face detector как отдельный npm-пакет (`@mediapipe/tasks-vision` или
   `face-api.js` — выбрать на этапе реализации, оба CPU, оба tflite).
3. Первый прогон на проде, калибровка порогов по логу (п. 8).
4. Клиент: переключатель + `CleanupScreen` + провайдер.
5. Поднять номер сборки в `flutter/pubspec.yaml`, `flutter analyze`, push в main —
   workflows подхватят (`src/**` → deploy, `flutter/**` → android/macos/ios).
