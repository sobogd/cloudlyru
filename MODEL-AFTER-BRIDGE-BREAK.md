# Почему после обрыва моста сессия переключается на локальную модель

Разбор по коду (Ветка `feature/agent-thread-ui`, коммит 792a9ed + UI-правки). Код пока
не менялся: ниже — механизм, доказательства из кода и три варианта, какой из них чинить.

## Коротко

К модели разговор после обрыва не «переключается» — её не выбирает мост заново. Её выбирает
**сам pi**, потому что при подъёме процесса заново (а после обрыва туннеля это происходит
почти каждый раз) мост не передаёт ему ни провайдера, ни модель: в команде запуска остаётся
только `--session-id`. А `default_model()` моста смотрит не на журнал сессии, а в
`~/.pi-bridge.json`, потом в первый провайдер `~/.pi/agent/models.json` — и первым там как раз
локальный `local`.

## Цепочка целиком

1. **Обрыв туннеля убивает процесс моста.** Туннель поднимается скриптом
   `agents/mac/run-tunnel.sh` (launchd `com.agent.mac-tunnel`), а мост —
   отдельным launchd-агентом `com.agent.pi-bridge` (`agents/pi-bridge/com.agent.pi-bridge.plist`).
   Связи между ними нет: скрипт туннеля мост не перезапускает.
2. **launchd поднимает мост заново** (`KeepAlive` + `ThrottleInterval` 5 с) — с пустым пулом:
   `POOL = Pool()` создаётся на старте процесса, все живые сессии харнесса теряются.
3. **Приложение возвращается к разговору**, вызывает `POST /projects/sessions` (открытие
   сессии), и сервер перекладывает его в мост (`src/projects/projects.controller.ts`).
4. **Мост поднимает процесс заново** — `Pool.open()` → `PiSession(cwd, session_id, model=None)`.
   При продолжении сессии приложение модель не присылает вовсе: в `agent_api.dart`
   (`openSession`) `modelKey` уходит только для новой сессии, и в контроллере это закреплено
   явно — «у существующей она уже записана в её файле».
5. **`PiSession._start()`** собирает команду:
   ```python
   provider, model = default_model()
   provider = self.provider or provider      # self.provider пуст
   model = self.model or model               # self.model пуст
   cmd = [pi, "--mode", "rpc", "--session-id", <id>]
   if provider: cmd += ["--provider", provider]
   if model: cmd += ["--model", model]
   ```
6. **`default_model()`** (agents/pi-bridge/server.py, функция `default_model`) при пустых
   `provider`/`model` в `~/.pi-bridge.json` идёт в `~/.pi/agent/models.json` и берёт **первого
   провайдера и его первую модель**. Провайдер `local` (llama.cpp) в этом файле идёт первым —
   отсюда и «постоянно локальная LLM».
7. **Запущенный pi видит `--session-id` и продолжает историю**, но модель уже другая. Что
   произошло, видно в журнале сессии: `pi` пишет туда запись `model_change` — значит смена
   модели при подъёме процесса в историю попадает и остаётся в ней навсегда.

## Доказательства из кода

| Факт | Где |
|---|---|
| При продолжении сессии модель не передаётся | `flutter/lib/features/agent/agent_controller.dart` — `open()`: `modelKey: sessionId == null ? modelKey : null` |
| Смена модели по кнопке живёт только в живом процессе | `agents/pi-bridge/server.py` — `PiSession.set_model()` → команда `set_model` в процесс; в `--provider/--model` при следующем старте это не попадает |
| При подъёме процесса модель берётся из настроек моста, а не из журнала | `agents/pi-bridge/server.py` — `PiSession._start()` + `default_model()` |
| Порядок провайдеров берётся из `models.json` как есть | `default_model()`: «для name, body in providers.items(): вернуть provider or name, model or models[0]» |
| Журнал сессии модель хранит | `agents/pi-bridge/server.py` — `read_session_meta()`: записи `model_change` с `provider` и `modelId` (первая побеждает: «она пишется при открытии») |
| Мост при старте пул теряет | `agents/pi-bridge/server.py` — `POOL = Pool()` на уровне модуля |

Отдельная деталь: `ClaudeSession._start()` модель тоже не восстанавливает (`self.model`
берётся из параметра конструктора). Там её подставляет сам Claude Code по `--resume`, поэтому
в приложении это не так заметно, но признак `local` в строке списка считается по одному лишь
провайдеру — `is_local_model({"provider": meta["provider"], "baseUrl": ""})` в
`_file_brief()`. Для закрытой сессии Claude Code вернуть «локальная» невозможно, у pi — можно,
и это второй способ увидеть «локальную» там, где её нет.

## Что чинить (на выбор)

### Вариант A. Запоминать модель сессии в самом мосте, рядом с процессом

При открытии сессии (`Pool.open()`, когда `key in self.sessions`) сохранять пару
`(provider, model)` и при подъёме процесса после смерти передавать её в `PiSession(...)`.
Просто и точно; минус — знание живёт в памяти процесса моста, и перезапуск моста (тот самый
случай обрыва туннеля) его сотрёт.

### Вариант B. Восстанавливать модель из журнала сессии

Перед `_restart()` (и при продолжении сессии в `Pool.open()`) читать последнюю запись
`model_change` из файла сессии и передавать её в запуск. Переживает что угодно, включая
перезапуск моста и мака; минус — лишнее чтение файла при каждом подъёме процесса и лишняя
связка «журнал → запуск», которой сейчас нет.

### Вариант C. Не терять процессы харнесса при обрыве моста — и заодно сам мост

Причина «часто случается» — не только в модели: обрыв туннеля гасит процессы харнесса и
роняет рабочие прогоны. Лечится сторожем (launchd `WatchPaths` на лог-файл моста,
`ProcessType: Interactive` + `KeepAlive` с `SuccessfulExit: false`, либо отдельный
`StartInterval`-агент): после перезапуска моста поднимать его снова. Процессы харнесса при
этом всё равно теряются (они дети моста), но паузы и лишние подъёмы процессов становятся
редкими, и вариацию модели видно реже.

Практично, по-моему, **B + C**: модель восстанавливается всегда (в том числе после перезапуска
моста и мака), а мост и туннель перестают расходиться.

## Почему «часто случается»

- Туннель и мост — **два независимых launchd-агента**: поднявшийся заново туннель не
  перезапускает мост, а упавший мост не тормошит туннель. Рассинхрон не лечится никем.
- `KeepAlive` у моста есть, но без `SuccessfulExit`, а стороннего надзора (WatchPaths/сторожа)
  нет.
- На VPS порт 18820 отдаётся reverse-туннелем; его конец на стороне VPS при переподключении
  нужно освобождать (в README есть строка про очистку залипших слушателей), и до этого момента
  сервер видит «мост недоступен».
- Долгие прогоны держат SSE-соединение часами (`proxy_read_timeout 1800s`, у моста поток
  закрывается по `Connection: close`): любой разрыв в этом соединении приложение видит как
  обрыв потока, даже когда сам мост жив.

## Что предлагаю сделать сейчас

1. Запись модели сессии в самом мосте (A) **плюс** восстановление из журнала (B) — чтобы
   разговор после обрыва продолжался той моделью, на которой его вели.
2. Сторож за мостом (C) — отдельно, потому что это уже про launchd и VPS, а не про код
   приложения.
