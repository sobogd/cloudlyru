# pi-bridge — мост между приложением CloudlyRu и агентами на маке

Раздел «Проекты» в приложении: выбираешь папку проекта — и дальше разговариваешь с агентом,
который работает в этой папке: читает файлы, правит их, запускает команды. Агентов (харнессов)
двое, и переключаются они в списке сессий проекта:

| Харнесс | Протокол | Модели |
|---|---|---|
| [pi](https://github.com/earendil-works/pi) (`@earendil-works/pi-coding-agent`) | `pi --mode rpc`, JSON-RPC по stdio | локальная llama.cpp и любые удалённые провайдеры |
| [Claude Code](https://claude.com/claude-code) | `claude --print --input-format stream-json --output-format stream-json` | свои (подписка или ключ на маке) |

У pi модель по умолчанию — та же локальная (`llama.cpp` на этом маке, `qwen/qwen3.5-9b`), что и
у раздела «Чат».

```
телефон / мак (приложение CloudlyRu)
   │ HTTPS + SSE, сессия приложения
сервер CloudlyRu (VPS, src/projects)  →  http://127.0.0.1:18820
   │ reverse-SSH туннель мака (jevel.ai/agents/run-dsh-tunnel.sh, ком.agent.dsh-reverse-tunnel)
мост  agents/pi-bridge/server.py, 127.0.0.1:18820
   │ JSON-строки по stdio, процесс на сессию
pi    pi --mode rpc  (cwd = папка проекта)
   └── llama.cpp 127.0.0.1:1234
```

Схема ровно та же, что у поиска (18814) и телефона (18816) в разделе «Чат»: порт открыт
только на loopback **обоих** концов туннеля, наружу не смотрит никто, поэтому ни TLS, ни
токенов на этом плече нет — доступ к разделу закрыт сессией приложения, как у остальных
разделов. В сборке приложения нет ни адреса моста, ни порта туннеля.

Мост — тонкий адаптер и не более: он не думает, не хранит историю и не знает про модели.
История — файлы сессий pi (`~/.pi/agent/sessions/--<путь>--/`), инструменты, контекст и
сжатие — тоже pi. Поэтому разговор, начатый в приложении, виден в терминале (`pi -r`), и
наоборот.

## Что делает мост

| Ручка | Зачем |
|---|---|
| `GET /health` | жив ли мост, какие харнессы стоят и что в пуле процессов |
| `GET /harnesses` | харнессы на маке: имя, версия, доступность |
| `GET /models?harness=` | модели харнесса: у pi — локальная и удалённые, у Claude Code — его собственные |
| `GET /providers` | провайдеры и признак «ключ задан» (сами ключи наружу не уходят) |
| `POST /providers` | создать или изменить своего провайдера (`models.json`) |
| `POST /providers/probe` | проверить адрес и ключ и получить список моделей провайдера |
| `POST /providers/key` | задать или убрать ключ встроенного провайдера (`auth.json`) |
| `DELETE /providers/<key>` | удалить своего провайдера |
| `GET /projects` | проекты: корни из allowlist плюс папки с `.git` внутри них |
| `GET /sessions?path=<папка>` | сессии проекта из файлов истории: у каждого харнесса свои, с пометкой чей |
| `POST /sessions` | открыть сессию: поднять процесс харнесса в папке проекта (`harness=pi\|claude`) |
| `GET /sessions/<id>` | модель, расход контекста, занятость |
| `GET /sessions/<id>/messages` | переписка в виде, готовом для экрана (читается из файла, процесс не нужен) |
| `GET /sessions/<id>/events` | подключиться к уже идущему прогону (SSE), ничего не отправляя агенту |
| `POST /sessions/<id>/prompt` | отправить сообщение; ответ идёт потоком SSE |
| `POST /sessions/<id>/abort` | остановить генерацию |
| `POST /sessions/<id>/compact` | сжать контекст |
| `POST /sessions/<id>/model` | сменить модель у открытой сессии |
| `POST /sessions/<id>/close` | закрыть процесс, историю оставить (освобождает память мака) |
| `DELETE /sessions/<id>` | удалить сессию: процесс гасится, файл истории и папка сессии стираются |
| `POST /sessions/purge` | убрать старые сессии проекта: старше N дней и/или кроме K свежих |

Наружу эти ручки отдаёт сервер приложения (`src/projects`, префикс `/projects/*`) — приложение
ходит только в него.

События потока: `delta`, `reasoning`, `tool_call`, `tool_start`, `tool_update`, `tool_end`,
`status`, `usage`, `ui`, `done`, `error`. Полный список — в `server.py`, в `_prompt`.

Ответ агента приходит блоками в порядке появления: кусок текста, карточка вызова инструмента,
снова текст. Так разговор читается в том порядке, в каком шёл, а не «весь текст сверху, все
карточки снизу»: блоки адресуют карточки по идентификатору, поэтому вывод инструмента в ответе
не дублируется. Рядом с `blocks` в каждом элементе остаются `text`, `reasoning` и `tools` —
сборка приложения, которая про блоки ещё не знает, покажет ответ как раньше.

Что приложение показывает из этого: занятость окна модели в токенах и процентах (сколько
свободно), расход за сессию (вход, выход, кэш, всего), счётчики сообщений и вызовов
инструментов, время начала и последней активности, путь к файлу сессии. Всё это мост берёт из
`get_state` и `get_session_stats` pi и обновляет перед каждым ответом — сам pi числа не пушит.

Настройки — `~/.pi-bridge.json` (создаётся при первом запуске, режим 600): порт, allowlist
корней, глубина поиска проектов, провайдер и модель по умолчанию, а также `claude_config_dir` —
профиль Claude Code (см. ниже). Если провайдер и модель pi не заданы, берётся первая модель из
`~/.pi/agent/models.json`.

Поле `token` в настройках пустое и таким должно остаться: мост виден только с loopback, а
запросы к нему делает сервер приложения. Токен нужен лишь в случае, если мост когда-нибудь
выставят наружу — тогда он включается в `~/.pi-bridge.json`, и сервер шлёт его из своего
окружения.

## Установка

```bash
cp agents/pi-bridge/com.agent.pi-bridge.plist ~/Library/LaunchAgents/
launchctl load ~/Library/LaunchAgents/com.agent.pi-bridge.plist
curl -s http://127.0.0.1:18820/health
curl -s http://127.0.0.1:18820/projects | head -c 400
```

На VPS порт появляется из reverse-SSH туннеля мака: в `jevel.ai/agents/run-dsh-tunnel.sh`
для него есть строка `-R 127.0.0.1:18820:127.0.0.1:18820` (и порт перечислен в очистке
залипших слушателей — без этого туннель не переподнимется после обрыва). После правки
скрипта туннель перезапускается:

```bash
launchctl kickstart -k gui/$(id -u)/com.agent.dsh-reverse-tunnel
ssh root@<VPS> 'ss -ltn | grep 18820'          # порт должен слушать loopback
ssh root@<VPS> 'curl -s http://127.0.0.1:18820/health'
```

Корни правятся в `~/.pi-bridge.json` (`roots`): по умолчанию это `~/work`. Внутри корней мост
показывает папки, в которых есть чем работать: свой `.git`, история pi или история Claude Code.
Плюс к обходу на заданную глубину (`depth`, по умолчанию 2) список дополняется папками из самих
историй — у каждой сессии записан её рабочий каталог, поэтому проект находится и на большей
глубине. Так в списке появился, например, `~/work/tangem`: своего `.git` у него нет (внутри
лежат репозитории), зато Claude Code работал именно в нём. Файловой системы наружу нет: папки
вне корней не показываются, даже если сессия когда-то была запущена там.

## Локальная модель или удалённая по API

Модель выбирается в приложении: в сессии — «Ещё → Модель», и она же запоминается как модель по
умолчанию для новых сессий. Список берётся у самого pi (`pi --list-models`), поэтому в нём
ровно то, что он действительно может запустить, с окном контекста и признаком «умеет
размышления». Локальные модели помечены отдельно от удалённых: у локальной адрес — loopback
(llama.cpp на этом маке), у удалённой — внешний.

Ключи от API живут **только на маке**: приложение и сервер их не хранят, а сохранённый ключ
никогда не читается обратно — наружу уходит лишь признак «задан» и его длина. Провайдеры
добавляются в приложении (раздел «Проекты» → иконка ключа → «Модели и ключи»): там есть форма
с адресом и ключом, кнопка проверки и подтягивания списка моделей у провайдера, и отдельный
ввод ключа для встроенных провайдеров pi. Мост пишет это в те же файлы, что правил бы человек, —
`~/.pi/agent/models.json` и `~/.pi/agent/auth.json` (прежний файл остаётся рядом копией `.bak`,
права 600). Провайдера по умолчанию удалить нельзя: на нём работает мак, когда модель не выбрана.

То же самое можно сделать руками, если так удобнее:

```bash
# 1) встроенный провайдер: ключ идёт в ~/.pi/agent/auth.json (режим 600) или в переменную окружения
pi            # в интерактивном режиме /login и выбрать провайдера

# 2) свой OpenAI-совместимый провайдер — в ~/.pi/agent/models.json, рядом с local
```

```jsonc
{
  "providers": {
    "local": { "...": "llama.cpp на 127.0.0.1:1234" },
    "deepseek": {
      "name": "DeepSeek API",
      "baseUrl": "https://api.deepseek.com/v1",
      "apiKey": "…",              // ключ читается только локально, наружу уходит лишь признак «задан»
      "api": "openai-completions",
      "models": [
        { "id": "deepseek-chat", "name": "DeepSeek Chat", "contextWindow": 128000, "maxTokens": 8192 }
      ]
    }
  }
}
```

После правки файла список в приложении обновится сам (кэш моста — минута). Провайдер без ключа
показывается в выборе серым с подписью «нужен ключ на маке»: выбрать его можно, но ответа не
будет. Подробности про провайдеров и ключи — в документации pi (`docs/providers.md`,
`docs/custom-provider.md`).

Сессия помнит свою модель: у неё она записана в файле, и в списке сессий видно, чем считался
разговор — локально или по API. Смена модели внутри сессии разговор не перезапускает.

## Claude Code: профиль и разрешения

Две вещи, без которых он молчит или отвечает «Not logged in», хотя в терминале всё работает:

**Профиль.** У Claude Code профилей может быть несколько, и различаются они переменной
`CLAUDE_CONFIG_DIR` (внутри профиля лежат и учётные данные, и история разговоров). Мост запускает
Claude Code не из твоей оболочки, а из своего окружения launchd, где переменных оболочки нет,
поэтому профиль задаётся настройкой `claude_config_dir` в `~/.pi-bridge.json`:

```jsonc
{
  "claude_config_dir": "/Users/<user>/.claude-work",  // профиль, из которого Claude Code залогинен
  "claude_permission_mode": "bypassPermissions"      // подтверждать в headless-режиме некому
}
```

Если настройка пуста, берётся `CLAUDE_CONFIG_DIR` из окружения моста, а если и его нет — профиль
по умолчанию `~/.claude`. История разговоров ищется в `projects` того же профиля: при чужом
профиле список сессий выглядел бы пустым при живых файлах на диске.

**Разрешения.** В потоковом режиме подтверждать некому, поэтому сессия стартует с
`--permission-mode bypassPermissions` — тем же «разрешать всё», что и у pi. Другие значения
(`acceptEdits`, `dontAsk`, `plan`) тоже работают: они ограничивают агента на уровне самого
Claude Code, и это единственный способ сузить его права, не переписывая мост.

Ключи и подписка Claude Code — его собственные и остаются на маке; приложение в них не
вмешивается и в экране «Модели и ключи» их не показывает (там только провайдеры pi).

## Диагностика

```bash
launchctl list | grep pi-bridge
tail -20 /tmp/pi-bridge.err.log        # автоответы агента тоже здесь
```

| Что видно | Что значит |
|---|---|
| «мост недоступен» в приложении | мост не поднят, туннель отключился или мак спит |
| Claude Code отвечает «Not logged in» | не тот `claude_config_dir` в настройках моста |
| `401` от сервера приложения | истекла сессия приложения, а не отказ моста |
| «сессия занята» | в этой сессии уже идёт генерация (в том числе из терминала) |
| пустой список проектов | в корнях нет папок с `.git` — проверить `roots` в `~/.pi-bridge.json` |
| `501`/`502` на `/projects/*` | сервер не видит мост: смотреть `PI_BRIDGE_URL` в окружении сервера |

## Что важно знать

**Уборка старых разговоров.** У Claude Code в одной папке их копятся сотни (`~/work/tangem` —
246), и удалять их по одному бессмысленно. Ручка `/sessions/purge` убирает разговоры по правилу:
старше N дней и/или всё, кроме K самых свежих. Оба условия складываются, и хотя бы одно
обязательно — без него ручка отказывает, чтобы «убрать старое» не стало «удалить всё». Свежие
разговоры защищены всегда, независимо от порога. В приложении это кнопка «Убрать старые» в списке
сессий: она показывает, сколько уйдёт по каждому правилу, до подтверждения.

**Закрытая сессия — не ошибка.** История, состояние и удаление работают и без живого процесса:
переписка читается прямо из файла сессии, «стоп» и «закрыть» на уже закрытой сессии отвечают
успехом (останавливать нечего). Так приложение не получает отказов на ровном месте — после
перезапуска моста или остановки процесса по простою.

**Идущий прогон можно смотреть.** Если ответ уже пишется (его начали с другого устройства),
приложение подключается к нему ручкой `/events` и показывает текст со стороны. Разрыв этого
соединения прогон не прерывает: за прерывание отвечает `abort`, и только он.

**Один клиент на сессию.** Два писателя в один JSONL-файл pi развели бы разговор, поэтому
занятая сессия отвечает `409`, а не принимает второй запрос. Сессия, открытая в терминале на
маке, для моста не «занята» — он про неё не знает; если хочется работать в двух местах сразу,
в приложении лучше начать новую сессию.

**Подтверждений нет.** Политика раздела — «разрешать всё без вопросов»: у pi в RPC-режиме
диалоги приходят от расширений событием `extension_ui_request`, и мост отвечает на них сам
(`confirm` → да, `select` → первый вариант, `input` → отмена). Каждый автоответ пишется в
`/tmp/pi-bridge.err.log` и показывается в переписке отдельной строкой — по нему видно, что
агент сделал без человека.

**Песочницы у pi нет** (см. `docs/security.md` самого pi): инструменты работают с правами
пользователя, поэтому единственная граница — allowlist корней в настройках моста и то, что
порт виден только на loopback обоих концов туннеля.

**Процессы гасятся по простою** (30 минут): каждый живой процесс pi держит контекст модели в
памяти, а память на этом маке дороже пары секунд на запуск. Продолжение разговора после
остановки поднимает процесс заново — сессия лежит в файле, ничего не теряется.
