# bridge — мост между приложением CloudlyRu и агентами на маке

Раздел «Проекты» в приложении: общий список разговоров со всех проектов, а новая сессия
заводится мастером «папка → модель» — и дальше разговариваешь с агентом, который работает в этой
папке: читает файлы, правит их, запускает команды. Агентов (харнессов) двое, и их разговоры
показываются в списке вместе, различаясь значком:

| Харнесс | Протокол | Модели |
|---|---|---|
| [Claude Code](https://claude.com/claude-code) | `claude --print --input-format stream-json --output-format stream-json` | свои (подписка или ключ на маке) |
| llm-harness | gRPC на `127.0.0.1:9000` + SSE на `127.0.0.1:9001` | своя (`mtplx — qwen3.8-27b`, локальная) |

```
телефон / мак (приложение CloudlyRu)
   │ HTTPS + SSE, сессия приложения
сервер CloudlyRu (VPS, src/projects)  →  http://127.0.0.1:18820
   │ reverse-SSH туннель мака (cloudlyru/agents/mac/run-tunnel.sh, com.agent.mac-tunnel)
мост  agents/bridge/server.py, 127.0.0.1:18820
   ├── claude --print stream-json   (cwd = папка проекта)
   └── llm-harness gRPC 127.0.0.1:9000 (локальная модель на маке)
```

Схема: порт открыт
только на loopback **обоих** концов туннеля, наружу не смотрит никто, поэтому ни TLS, ни
токенов на этом плече нет — доступ к разделу закрыт сессией приложения, как у остальных
разделов. В сборке приложения нет ни адреса моста, ни порта туннеля.

Мост — тонкий адаптер и не более: он не думает, не хранит историю и не знает про модели.
История — файлы сессий Claude Code в профиле (`<профиль>/projects/`), у llm-harness —
в его собственном хранилище; инструменты и контекст — за самими харнессами.

## Что делает мост

| Ручка | Зачем |
|---|---|
| `GET /health` | жив ли мост, какие харнессы стоят и что в пуле процессов |
| `GET /harnesses` | харнессы на маке: имя, доступность |
| `GET /models?harness=` | модели харнесса: у Claude Code — его собственные, у llm-harness — своя, плюс уровни усилия |
| `GET /projects` | проекты: корни из allowlist плюс папки с `.git` внутри них |
| `GET /sessions?path=<папка>` | сессии проекта из истории: у каждого харнесса свои, с пометкой чей; без `path` — сессии всех проектов одним списком (новые по дате создания сверху) |
| `POST /sessions` | открыть сессию: поднять процесс харнесса в папке проекта (`harness=claude|harness`) |
| `GET /sessions/<id>` | модель, расход контекста, занятость |
| `GET /sessions/<id>/messages` | переписка в виде, готовом для экрана (читается из файла, процесс не нужен) |
| `GET /sessions/<id>/events` | подключиться к уже идущему прогону (SSE), ничего не отправляя агенту |
| `POST /sessions/<id>/prompt` | отправить сообщение; ответ идёт потоком SSE |
| `POST /sessions/<id>/queue` | дописать сообщение в занятую сессию: уйдёт агенту по завершении текущего прогона |
| `POST /sessions/<id>/abort` | остановить генерацию |
| `POST /sessions/<id>/compact` | сжать контекст |
| `POST /sessions/<id>/model` | сменить модель у открытой сессии |
| `POST /sessions/<id>/effort` | сменить уровень усилия (у llm-harness есть свой набор уровней; пусто — умолчание модели) |
| `POST /sessions/<id>/name` | переименовать разговор (имя пишется в его журнал, процесс не нужен) |
| `DELETE /sessions/<id>` | удалить сессию: процесс гасится, файл истории и папка сессии стираются |

Наружу эти ручки отдаёт сервер приложения (`src/projects`, префикс `/projects/*`) — приложение
ходит только в него.

События потока: `delta`, `reasoning`, `tool_call`, `tool_start`, `tool_update`, `tool_end`,
`status`, `usage`, `ui`, `snapshot`, `ping`, `done`, `error`. Полный список — в `server.py`, в `_prompt`.

`snapshot` приходит первым событием, когда приложение подключается к уже идущему прогону (ручка
`/sessions/<id>/events`): это накопленный текст текущего ответа. Подключиться к потоку с середины
нельзя — дельты, вышедшие между снимком истории и подпиской, потерялись бы, — поэтому приложение
заменяет снимком хвост переписки и дальше дописывает обычные дельты. Пока агент молчит, поток
раз в 15 секунд шлёт событие `ping`: без трафика мобильный NAT и промежуточные прокси рвут
соединение молча, и приложение не отличает такую смерть от долгой работы. По `ping` приложение
знает, что связь жива, и по его отсутствию понимает, что поток умер.

Ответ агента приходит блоками в порядке появления: кусок текста, карточка вызова инструмента,
снова текст. Так разговор читается в том порядке, в каком шёл, а не «весь текст сверху, все
карточки снизу»: блоки адресуют карточки по идентификатору, поэтому вывод инструмента в ответе
не дублируется. Рядом с `blocks` в каждом элементе остаются `text`, `reasoning` и `tools` —
сборка приложения, которая про блоки ещё не знает, покажет ответ как раньше.

Что приложение показывает из этого: занятость окна модели в токенах и процентах (сколько
свободно), расход за сессию (вход, выход, кэш, всего), счётчики сообщений и вызовов
инструментов, время начала и последней активности.

Настройки — `~/.agent-bridge.json` (создаётся при первом запуске, режим 600): порт, allowlist
корней, глубина поиска проектов, уровень усилия Claude Code по умолчанию, `claude_config_dir` —
профиль Claude Code (см. ниже), и `harness` — адреса llm-harness (gRPC и SSE, по умолчанию
`127.0.0.1:9000` и `http://127.0.0.1:9001`).

Поле `token` в настройках пустое и таким должно остаться: мост виден только с loopback, а
запросы к нему делает сервер приложения. Токен нужен лишь в случае, если мост когда-нибудь
выставят наружу — тогда он включается в `~/.agent-bridge.json`, и сервер шлёт его из своего
окружения.

## Установка

```bash
cp agents/bridge/com.agent.bridge.plist ~/Library/LaunchAgents/
launchctl load ~/Library/LaunchAgents/com.agent.bridge.plist
curl -s http://127.0.0.1:18820/health
curl -s http://127.0.0.1:18820/projects | head -c 400
```

На VPS порт появляется из reverse-SSH туннеля мака: в `cloudlyru/agents/mac/run-tunnel.sh`
для него есть строка `-R 127.0.0.1:18820:127.0.0.1:18820` (и порт перечислен в очистке
залипших слушателей — без этого туннель не переподнимется после обрыва). После правки
скрипта туннель перезапускается:

```bash
launchctl kickstart -k gui/$(id -u)/com.agent.mac-tunnel
ssh root@<VPS> 'ss -ltn | grep 18820'          # порт должен слушать loopback
ssh root@<VPS> 'curl -s http://127.0.0.1:18820/health'
```

Корни правятся в `~/.agent-bridge.json` (`roots`): по умолчанию это `~/work`. Внутри корней мост
показывает папки, в которых есть чем работать: свой `.git`, история Claude Code в профиле
или каталог `.llm-harness`. Плюс к обходу на заданную глубину (`depth`, по умолчанию 2) список
дополняется папками из самих историй — у каждой сессии записан её рабочий каталог, поэтому
проект находится и на большей глубине. Файловой системы наружу нет: папки вне корней не
показываются, даже если сессия когда-то была запущена там.

## llm-harness

Сам llm-harness — отдельный сервис на маке (gRPC-адрес и SSE-база задаются в `harness`
настроек моста): модель, инструменты и сессии живут у него, мост только пересылает
промпты и складывает его события в тот же поток, что и у Claude Code. У llm-harness одна
модель (`mtplx — qwen3.8-27b`) и свой набор уровней усилия. Если llm-harness не поднят,
харнесс в `/harnesses` значится недоступным, и сессии на нём открыть нельзя — остальной
мост от этого не страдает.

## Claude Code: модели, усилие, профиль и разрешения

**Модели.** Список мост отдаёт из встроенного каталога установленного Claude Code: псевдонимы
семейств (`fable`, `opus`, `opusplan`, `sonnet`, `haiku`) и конкретные версии вместе с
1M-вариантами (`claude-opus-4-6[1m]` и т. п.). Псевдоним — самый устойчивый выбор: Claude Code
сам разрешает его в новейшую версию, доступную аккаунту, и список переживает выход новых версий;
конкретная версия нужна, когда надо вернуться на прежнюю или взять большее окно. Список
обновляется вместе с Claude Code — он повторяет его каталог, а не документацию.

**Усилие.** Сколько модель думает над ответом — флаг `--effort` со значениями `low`, `medium`,
`high`, `xhigh`, `max`. Пусто — «как решает Claude Code»: умолчание у моделей разное. Смена
уровня, как и смена модели, перезапускает процесс и продолжает разговор из файла.

Две вещи, без которых он молчит или отвечает «Not logged in», хотя в терминале всё работает:

**Профиль.** У Claude Code профилей может быть несколько, и различаются они переменной
`CLAUDE_CONFIG_DIR` (внутри профиля лежат и учётные данные, и история разговоров). Мост запускает
Claude Code не из твоей оболочки, а из своего окружения launchd, где переменных оболочки нет,
поэтому профиль задаётся настройкой `claude_config_dir` в `~/.agent-bridge.json`:

```jsonc
{
  "claude_config_dir": "/Users/<user>/.claude-work",  // профиль, из которого Claude Code залогинен
  "claude_permission_mode": "bypassPermissions"      // подтверждать в headless-режиме некому
}
```

Если настройка пуста, берётся `CLAUDE_CONFIG_DIR` из окружения моста, а если и его нет — профиль
по умолчанию `~/.claude`. История разговоров ищется в `projects` того же профиля: при чужом
профиле список сессий выглядел бы пустым при живых файлах на диске.

**Разрешения.** В потоковом режиме подтверждать некому, поэтому сессия стартует с
`--permission-mode bypassPermissions`. Другие значения (`acceptEdits`, `dontAsk`, `plan`) тоже
работают: они ограничивают агента на уровне самого Claude Code, и это единственный способ
с сузить его права, не переписывая мост.

Ключи и подписка Claude Code — его собственные и остаются на маке; приложение в них не
вмешивается.

## Диагностика

```bash
launchctl list | grep bridge
tail -20 /tmp/agent-bridge.err.log
```

| Что видно | Что значит |
|---|---|
| «мост недоступен» в приложении | мост не поднят, туннель отключился или мак спит |
| Claude Code отвечает «Not logged in» | не тот `claude_config_dir` в настройках моста |
| llm-harness недоступен в `/harnesses` | сам llm-harness не поднят на маке |
| `401` от сервера приложения | истекла сессия приложения, а не отказ моста |
| «сессия занята» | в этой сессии уже идёт генерация (в том числе из терминала) |
| пустой список проектов | в корнях нет папок с `.git` — проверить `roots` в `~/.agent-bridge.json` |
| `501`/`502` на `/projects/*` | сервер не видит мост: смотреть `BRIDGE_URL` в окружении сервера |

## Что важно знать

**Разговоры удаляются по одному.** У Claude Code в одной папке их копятся сотни
(`~/work/tangem` — 246), поэтому пугаться длинного списка не стоит: строка удаляется иконкой
прямо в списке, а удаление стирает и файл истории, и папку сессии рядом с ним (результаты
инструментов, служебные пометки).

**Закрытая сессия — не ошибка.** История, состояние и удаление работают и без живого процесса:
переписка читается прямо из файла сессии, «стоп» на уже закрытой сессии отвечает
успехом (останавливать нечего). Так приложение не получает отказов на ровном месте — после
перезапуска моста или остановки процесса по простою.

**Идущий прогон можно смотреть.** Если ответ уже пишется (его начали с другого устройства),
приложение подключается к нему ручкой `/events` и показывает текст со стороны. Разрыв этого
соединения прогон не прерывает: за прерывание отвечает `abort`, и только он.

**Сообщение в занятую сессию не отклоняется.** Оно встаёт в очередь и уезжает агенту, как
только тот закончит текущий прогон (очередь держит мост — так одинаково работают оба
харнесса). Поток при этом не закрывается между прогонами: приложение видит и текущий ответ,
и ответ на своё сообщение, а в строке состояния показывает «в очереди: N». Два устройства
могут дописывать в один разговор — второй не получит отказа. Единственное, чего по-прежнему
нельзя, — чтобы два агента считали один разговор одновременно: у сессии один контекст.

**Состояние работы живёт на сервере.** Он раз в пять секунд спрашивает у моста, что считается, и
отдаёт приложению снимок (`GET /projects/activity`): что идёт сейчас и что закончилось за
последние полчаса. Поэтому, вернувшись в приложение, видно «✓ готово» у разговоров, которые
дописались без вас. Настоящих уведомлений в фоне нет — для них нужен push-канал (FCM/APNs).

**Песочницы нет**: инструменты работают с правами пользователя, поэтому единственная граница —
allowlist корней в настройках моста и то, что порт виден только на loopback обоих концов туннеля.

**Процессы гасятся по простою** (30 минут): каждый живой процесс Claude Code держит контекст
модели в памяти, а память на этом маке дороже пары секунд на запуск. Продолжение разговора
после остановки поднимает процесс заново — сессия лежит в файле, ничего не теряется.
